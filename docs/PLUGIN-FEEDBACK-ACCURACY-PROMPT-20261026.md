## 二、功能 A：在招聘网页上给轻量反馈

### 2.1 用户体验

用户授权网站后正常浏览岗位，即使没有打开插件 popup，也能在当前招聘网页上看到轻量提示，知道识别和保存的结果。

默认采用页面右下角的小 Toast，适配窄窗口；标明「帮你理」，成功提示约 4 秒后消失，可手动关闭。不要遮住投递按钮、表单、聊天区或页面主要内容，不抢焦点，不要求用户确认，不连续堆叠弹窗。

Toast 可提供一个「查看台账」操作：由用户点击后打开当前配置的后台，定位实际记录或对应列表。复用当前后台地址与登录深链机制，不写死开发端口，不自动打开新标签。

### 2.2 提示必须与真实处理状态一致

| 实际状态 | 提示示例 | 要求 |
|---|---|---|
| 已开始有效岗位的采集，处理稍慢 | 正在整理当前岗位… | 可延迟约 800ms 显示，快路径直接显示结果，避免闪烁 |
| 服务端确认保存了未投递记录 | 当前岗位已计入「看过没投」 | 普通浏览不误称“已投递” |
| 服务端确认补全原记录 | 当前岗位信息已更新 | 不冒充新增一条 |
| 已保存，但部分字段缺失 | 当前岗位已计入「看过没投」，部分信息待补充 | 明确保存成功不等于字段齐全 |
| 服务端确认申请阶段已更新 | 投递进展已更新到台账 | 只有确有投递/进展证据才使用此文案 |
| 只在本地入队，暂未上传成功 | 当前岗位待同步，连接恢复后自动重试 | 不能显示“已计入台账” |
| 服务端返回复核项 | 当前岗位信息需要确认 | 「查看」进入对应待确认入口 |
| 未绑定、授权不足或服务异常 | 尚未保存，请打开插件查看原因 | 给出已有诊断入口；能确定原因时用具体文案 |

若最终回执无法确定业务状态，使用准确的中性文案「当前岗位已保存到台账」，不要猜它属于哪个入口。

**成功判定必须依赖服务端确认的业务记录。** 提取到字段、本地队列成功、HTTP 200 或 `accepted=true` 都不单独等于入账成功。至少核对 `application_id` 和最终处理结果，复核/失败不能显示成功。事件 `processing_state=applied` 表示事件已应用，不等于岗位已经投递。

优先复用现有回执。如果需要区分新增、补全、无变化或岗位业务状态，应给回执补充明确字段并兼容旧格式，不能由 Toast 自行猜测。只有浏览时间更新而字段没有变化，自动浏览时应静默；用户主动点击采集则可反馈「该岗位已在台账中」。

### 2.3 列表、重复访问与异步回执

- 列表一次采到多个岗位时只显示一条汇总，例如「本页 8 个岗位已保存，2 个待同步」。按实际去重后的记录和回执计数，不按 DOM 卡片数或事件数报成功。
- 一页只显示一个 Toast；同一批次的状态变化更新原提示。重复滚动、DOM 更新、重复上传不反复弹窗。按岗位身份、实际结果和数据变化去重，并设置合理的频率上限。
- 回执须关联原始 tab、页面/路由版本和岗位身份。A 岗上传途中切换到 B 岗，A 的回执不能弹成「当前岗位已保存」。
- 后台页、已关闭标签或断网期间的旧任务完成后，把结果保留在插件状态中；不要在用户正在看的无关页面显示成功。
- popup 关闭、service worker 休眠恢复、多标签同时采集时仍能正确处理；不能把提示依赖于 popup 持续打开。
- 页面提示仅针对有效采集任务，不能在每个普通网页上显示“未识别到岗位”。长时间等待要转为待同步/失败状态，不能永久显示“正在整理”。

### 2.4 实现质量

样式与招聘网站隔离，避免全局 CSS 冲突或改变布局；处理重复注入、SPA 切换及权限撤销后的清理。提示可被辅助技术读取，普通提示使用不抢焦点的状态播报。动画克制，支持减少动态效果设置。

在插件设置里提供「页面采集提示」开关，默认开启；关闭后保留 popup 中的采集状态与错误记录。不要为页面 Toast 额外要求系统通知权限。

## 三、功能 B：提高岗位信息与 JD 的准确度

### 3.1 先找错在哪，再决定怎么改

用户仍反馈实际岗位识别不准。请先建立当前版本的问题清单，逐例区分：

- 抓错公司、岗位名、工作城市或岗位 ID。
- 页面有字段但没提取到。
- JD 少了任职要求、职责、某个段落，或被截断。
- 把推荐岗位、公司介绍、导航、投递须知等混进 JD。
- SPA/侧栏换岗后混用前一个岗位的信息。
- 抽取正确，但去重/匹配错误，入错记录或前端显示不一致。
- 页面本身未提供字段、尚未加载、需要登录，或访问验证阻挡。

不能把最后一类与算法错误混为一谈，也不能把字段留空全部排除在漏采统计之外。优先复现腾讯入口 `https://careers.tencent.com/search.html?pcid=40003`，并从当前真实页面补充失败样本，不只回放旧快照。

### 3.2 按证据选择识别方法

评估并实现确有收益的组合，逐项用样本证明：

1. **页面结构化数据**：检查当前岗位对应的 JobPosting / JSON-LD / microdata；核对 URL、岗位 ID 和可见标题，防止读到其他岗位或过期数据。
2. **站点适配器**：对重点官网建立经真实页面校准的选择器和区块边界，覆盖列表、详情、SPA 和侧栏；不要只依赖易变的样式类名。
3. **通用语义提取**：从岗位主体中的标题、标签和“岗位职责 / 任职要求”等区块提取。字段分别记录来源和把握度；避免取整页最长文本或平台名称当实际招聘公司。
4. **模板复用**：旧模板在另一个岗位验证正确后才稳定复用；结构变化要检测、降级和重学，不能“还能找到一个标题”就认定整页提取成功。
5. **可选模型辅助**：若规则仍不能可靠处理，评估使用授权岗位文本辅助字段提取或区块定位。保留原文引用、结构校验、超时回退和关闭开关；比较是否真实改善漏采和错误率。模型不能编造公司、城市、投递事实，也不能把改写后的摘要冒充原始 JD。

不要求为了接模型而接模型。优先解决页面范围、稳定身份和区块边界；如果模型没有配置或没有证明收益，明确报告即可。

### 3.3 JD 与岗位身份的硬要求

- JD 同时覆盖原页提供的职责与任职要求，保留原始段落和列表语义；原文全文与摘要分开保存。
- 只保存当前岗位内容，不混入相邻卡片和推荐岗位；展开后才出现的内容或未加载内容要如实标记不完整。
- 超长、未展开、加载失败、原页无全文，分别说明；不得静默截断后标“完整”。
- 同名不同 ID、跨域相同数字 ID、同 URL 不同侧栏岗位必须正确区分；后续详情应补全同一条列表记录。
- 空值补成有值不应被当成换岗；可靠的人工修正保留。异步提取结果回写前再次核对岗位身份。
- 字段缺失与是否已投递分开处理。可靠的普通浏览线索仍进「看过没投」，不能通过大量转待确认来提高所谓准确率。

## 四、按真实样本说明“能做到什么程度”

### 4.1 样本与结果必须可核对

重点站点沿用：腾讯、网易、小米、OPPO、拼多多、米哈游、美团、快手、实习僧、BOSS。每站至少当前列表 1 页、不同详情 3 个；选择不同岗位类型和页面结构，有失败样本必须保留。BOSS 使用用户正常登录的浏览器，不将登录/验证页算成功。

开发调试样本之外保留未用于调参的验收岗位，避免只适配几个已知页面。对照值应来自独立检查原网页，不能把提取器结果原样存为正确答案。

逐字段报告公司、标题、城市、招聘批次、岗位链接/ID；JD 另报章节覆盖、缺失段落、混入无关内容和截断情况。结果至少分为：正确、错误、原页有值但漏采、原页未提供、无法访问/未验证。

比较修改前后同一组样本；原网页已变化时单列，不能直接把变化解释为进步。字段精确率和召回率给出明确定义及原始数量，不能仅用“抓到多少条”代替准确率。

目标可沿用核心字段精确率 ≥98%、召回率 ≥95%，并要求验收样本中不串岗位、不误记投递、不重复建岗。目标不是保证；未达到就报告实际分子/分母、失败项和原因。少量样本通过不代表所有网站或页面达到相同水平。

### 4.2 能力报告必须包含这些结论

| 站点/页面类型 | 本轮样本数量 | 能可靠提取的内容 | 错误与漏采 | JD 完整性 | 是否准确入账 | 限制与下一步 |
|---|---:|---|---|---|---|---|
| 每站分别填写 | 实际数量 | 有证据的能力 | 保留具体失败样本 | 职责/要求/段落 | 核对台账 | 可修、需登录、维护成本或未验证 |

最终明确区分：

- **已实现且本轮样本验证通过。**
- **支持但在特定结构下不稳定。**
- **当前不支持或不能取得所需信息。**
- **尚未验证，不能下结论。**

对可以改进的点说明采取了什么办法、改进了哪些样本；对暂时做不到的点说明具体原因及替代方式，如补充字段、打开详情补全文或手动纠正。不能只写“各站结构不同，无法保证”。

历史报告曾有预授权条件下的 9 个必选站、95 个列表记录和 27 个详情通过；这只是旧版本固定样本证据，不可直接复制为本轮准确度或用户当前页面的结论。

## 五、验收与交付

Toast 至少验证：真实入账才成功提示、仅入队不报成功、待确认/失败文案准确、缺字段入账提示、列表合并提示、重复浏览不刷屏、主动采集有反馈、A→B 切换不串提示、多标签、关闭 popup、断网重试、关闭提示开关，以及「查看台账」定位正确。

准确度验收必须贯穿：**真实招聘页面 → 实际插件识别 → 服务端回执 → 正确业务记录 → 前端字段/JD → 正确 Toast**。本地 fixture 用于稳定回归，真实网站用于验证当前兼容性，结果分别报告。模拟回执和直接调用提取函数不能代替这一完整流程。

交付：

1. 实际代码改动与版本，轻量提示截图或录屏。
2. 可重复测试命令与结果，标清权限、登录态、数据环境和未完成项。
3. 按站点的修改前后对比、失败样本及能力边界报告。
4. 更新自测教程，让用户知道每种提示含义，以及怎样确认记录和 JD 已正确保存。

完成标准：**用户正常浏览时能轻量、准确地知道岗位是否入账；字段与 JD 的识别经过有证据的改进；无法可靠识别的场景有明确反馈和可用补救方式。**
