# 邮件阶段与轮次规则（2026-10-23 用户拍板）

这两条是**通用规则**，写在代码里，不是针对某几封邮件的特判。

## 规则一：笔试/测评与面试是两条独立记录，不合并

- 阶段映射：`assessment`（笔试/测评）与 `interview`（面试）各自成阶段；`offer / rejected / closed` 是终态，不进这套拆分。
- 匹配优先级（`server/src/domain/mailMatching.js` `findProgressCandidates`）：
  1. 先按站点/申请号精确匹配；
  2. 再按「公司 + 相似岗位」匹配，且**只取同阶段的那条**（面试邮件只找面试记录，笔试邮件只找笔试记录）；
  3. 如果同公司同岗位的记录全都停在**另一个阶段**（例如已有笔试、来的是面试），**返回空**，交给人工新建，绝不硬并成一条；
  4. 记录还停在 `applied / pending`（还没进入阶段）时，仍然推进同一条，不拆分。
- 端到端表现：出现第 3 种情况时，待确认里会生成一条 `reason_code = STAGE_SPLIT_REQUIRED` 的复核项，摘要写明
  「这封是面试进展；已有记录属于另一个阶段，建议单独建一条，不要合并」。

**为什么这样定**：同一条记录如果先笔试后面试，状态栏只能显示一个值，看不出「笔试已过、现在在面」；
拆成两条后，按收到时间倒序就能看出先后：面试那条在上、笔试那条在下，时间线自洽。

## 规则二：同名邮件按收到时间推进轮次

- 同一公司 + 同一岗位又收到一封**更晚**的面试邮件时，视为进入下一轮：`interview_round + 1`，`round_label = 第N面`。
- 锚点用**本阶段原信收到时间**（`stage_received_at`），不用 `last_progress_at`（人工确认会把它改成“现在”，会把规则废掉）。
- 第一封：`第1面`；之后每收到一封更晚的：`第2面`、`第3面`……
- 如果邮件本身明确写了轮次（`一面/二面/三面/终面/HR面`），以邮件为准，不再自增（`round_label` 已显式给出时跳过）。
- 实现位置：`server/src/domain/reviews.js` 的 `applyReviewChangesToApplication`（人工确认/关联路径）。

**为什么这样定**：网易那两封「面试邀请函」「面试时间收集」标题几乎一样，靠标题无法区分一面还是二面；
按用户要求，最新收到的那封视为推进到下一轮，时间就是排序依据。

## 规则三：待确认列表按邮件收到时间倒序

`reviewList` 的排序从 `created_at`（入库时间）改成 `COALESCE(mail.received_at, created_at)` 倒序：
列表从上到下就是「最新收到的邮件 → 最旧」，和用户看邮件的直觉一致。

## 规则四：待确认可人工修改公司/岗位

- 「不对，我来改」展开后，**公司和岗位始终可编辑**（以前只有“按邮件新建”时才出现这两个输入框）。
- 选中已有台账记录 + 改了公司/岗位 → 写回该记录（`link` 带上 `changes`）。
- 没选记录但填了公司 + 岗位 → 自动按邮件新建（`create`）。
- 两个都没填也没选记录 → 明确提示「请先搜索选择一条本人记录；或填写公司/岗位后按邮件新建」。
