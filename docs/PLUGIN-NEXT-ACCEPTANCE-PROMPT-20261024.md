## 2. 明确本轮产品行为

### 正常详情页/详情侧栏

首次授权当前站点后，无须刷新页面，自动识别当前岗位并进入未投递台账。之后用户在已授权站点正常浏览其他岗位，无须反复打开插件、点击「采集」或逐条确认。

自动浏览采集可以沿用真实可见停留至少 3 秒的防误触机制，但应保证达到条件后自动上传、自动入账。首次显式授权采集走独立事件，不伪造停留时长。

对于页面明确提供公司、岗位名称和稳定岗位标识，且字段通过质量校验的普通岗位，应直接入账。不得通过把大多数正常岗位放进待确认来规避自动入账要求。缺少非必要的批次、薪资或经验信息，不应阻塞可靠岗位入账。

真正缺少关键字段、来源冲突或身份不确定的记录保留待确认，并给出具体原因；不猜字段、不为了提高成功率绕过质量校验。用户点击采集是操作事实，不代表提取字段天然可信。

### 列表页

识别当前已加载的岗位卡片，逐条提取公司、名称、稳定链接/ID及页面已有字段。字段可靠的岗位可自动进入未投递台账，记录来源为「列表发现」；不为未打开的详情伪造浏览事件。

列表没有完整 JD 时标记「JD 待补充」。随后打开详情或侧栏，自动补全同一条记录，不能重复新建或用列表摘要覆盖完整 JD。

### 台账语义

采集记录统一 `has_applied=false`，业务状态为 `pending`，在「未投递/看过没投」对应入口可见；列表发现与详情浏览应能区分来源。没有投递成功证据，不能算已投递，不能影响已投递统计。

同岗位重复访问只合并或补全；同公司同名但不同 ID 的岗位不能误合并。人工修正的字段不得被抓取覆盖。事件处理状态中的 `applied` 与岗位业务状态中的 `applied` 含义不同，UI 必须正确映射。

## 3. 先建立真实扩展的端到端自测

使用支持扩展的真实 Chrome/Chromium 持久浏览器上下文，加载本轮实际扩展，连接实际测试后端和前端。记录浏览器版本、代码提交、扩展版本。使用独立测试用户、数据库和浏览器资料目录。

主验收必须走真实产品路径，不能用 mock `chrome.storage`、mock `chrome.runtime`、直接注入伪造事件、直接写数据库或单独调用 `__tounarCapture()` 代替。

每条主流程验证：

1. 打开真实岗位网页。
2. 从扩展 UI 完成首次站点授权；后续样本使用已授权状态自然浏览。
3. 验证脚本识别的字段及来源。
4. 以 `client_event_id` 串联本地队列、服务端回执和业务处理结果。
5. 验证服务端返回的 `application_id` 对应正确岗位；只进入 review 或仅接收 event 不算入账。
6. 在实际前端自动出现该记录，无须刷新；打开详情核对公司、标题、城市、批次及 JD 全文。
7. 重复浏览和重新加载后仍只有一条，状态仍是未投递。

至少分别跑通：首次授权即采、已授权新开详情页、SPA A→B、详情侧栏切换、列表→详情补全，以及关闭 popup 后继续处理。

本地 fixture 用于稳定复现和故障注入，真实网站用于验证当前兼容性，两种结果分别记录。真实数据集不能添加专门帮助识别的 `data-tounar-*` 钩子。

## 4. 用独立真值判断准确度

为每个测试页面保存脱敏 URL、采样时间、页面类型、人工核对字段和最小原文证据，形成可回归的 expected 数据。

预期值必须来自对原网页的独立核对，不能由待测提取器输出后原样存为答案。网页发生变化时记录需要复核，不能为了让测试通过自动修改 expected。

逐字段检查：公司、岗位名称、城市、招聘批次、完整 JD、岗位 ID/链接。结果分类为「正确、错误、原页存在但漏采、原页未提供」。

- JD 要检查职责和任职要求覆盖、是否混入推荐岗位/公司宣传/导航、是否截断和是否保留段落。字数大于 80 不是完整性证明。
- 公司取实际招聘方，不取平台品牌；城市取岗位工作地点；原文没有批次就留空。
- 验证多个 JD 区块、同名不同 ID、长标题、多城市、没有投递按钮但正文明确、列表侧栏等普通情况。

建议门槛：

- 正常样本中，公司、岗位身份和链接不得出现错误关联；重复入账、串岗位、误记已投递均为阻断问题。
- 原页有值的核心字段总体精确率 ≥98%、召回率 ≥95%；同时报告每站原始数量。
- 对人工事先判定「原页信息足够自动入账」的正常详情，准确自动入账率 ≥95%。分母在测试前冻结，不能按识别器成功与否或置信度事后筛选。
- 准确自动入账成功必须同时满足：字段正确、生成/合并到正确业务记录、前端自动可见；转待确认、只入队或只收到 HTTP 200 均不计成功。
- 在约定的非岗位页面测试集中误入账为 0。该结果只说明测试集表现，不能宣称所有网站零误识别。

## 6. 验证自动识别的持续可靠性

学习模板至少在真实扩展中完成：岗位 A 学习 → 岗位 B 用旧模板提取 → 核对字段来源与结果 → 重启后复用 → 结构变化后降级 → 重学恢复。

必须记录实际命中的模板版本和字段来源。模板命中时仍被站点适配器兜底补齐的字段要分别报告，不能把最终采集成功等同于模板全部成功。对 query/hash 路由及同域不同模板增加用例。

异常回归至少包括：

- 慢加载、SPA 快速换岗、A 岗异步结果在切到 B 后返回、同标题不同岗位 ID。
- 登录页、验证码页、首页、空列表、错误页、过期岗位、聊天页。
- 未配对、断网、后端 4xx/5xx、队列重试、浏览器重启、重复采集。
- 拒绝/撤销站点权限、暂停采集、用户人工修正。
- 超长 JD、多个 JD 区块、模板只剩标题仍能命中但公司/JD 失效。

断网应显示待上传，恢复后自动同步且不重复；未入账不得显示已入账。删除模板、撤销权限、清空队列是不同操作，结果要一致且可验证。

## 7. 本轮优先级与耗时要求

执行顺序：

1. 修复运行错误和成功状态误报。
2. 跑通真实扩展的自动采集、自动入账与前端显示。

## 8. 交付可重复执行的自测，而不只是一次报告

提供一个统一自测命令及必要参数，例如 `npm run test:plugin-acceptance`，实际名称由你实现后确定。区分稳定回归、需要联网的真实站点验收和需要登录的样本。失败退出码必须非零，受阻不能自动算通过。

自动生成 JSON 明细和可读报告，至少包含：

`site、url、page_type、expected、actual、field_result、extraction_source、template_version、client_event_id、processing_state、application_id、frontend_visible、duplicate_count、timings、error、evidence_path`

最终交付实际修复内容、运行命令、逐站结果、准确率和自动入账率的分子分母、关键截图/trace，以及剩余阻塞项。报告必须由实际测试结果支撑，不再手写错误的 9/10 统计。

完成标准是：我授权站点后正常浏览岗位，正确的信息自动进入未投递台账；查看详情能看到完整 JD；再次浏览不重复；错误页面不会污染台账。请围绕这个体验持续自测和修复，再报告结论。
