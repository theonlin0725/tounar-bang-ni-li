## 2. 阻断发现（有隔离复现）

### 问题 1：邮件复核被当作网页来源，邮件主题与正文仍不可见

位置：[ledger.js:213](../server/src/domain/ledger.js#L213)，前端分支：[reviews.js:83](../web/assets/js/views/reviews.js#L83)。

`sourceFromRow()` 以 `source_payload_json` 存在作为页面来源条件。但邮件同步也会生成带 payload 的 `mail_progress_detected` 事件，不能用是否有事件区分页面和邮件。

隔离复现：建立含主题、发件域名和正文片段的邮件事件，经真实 `processMailEvent()` 生成复核，再读取列表和详情。两处都返回 `source.type='page'`，而 `evidence.body_excerpt` 明明仍有正文。前端因此进入网页分支，隐藏邮件主题/正文，并显示“按页面信息新建一条”。

验收库只读统计有 **16 条 open 邮件复核具有关联事件及 payload**，符合该错误分支条件。这不是“历史邮件没授权正文”就能解释的问题。

修复方向：查询并使用事件 `source_method`、原信关联与可靠来源字段判断；列表和详情保持一致。补邮件带事件、老邮件无事件、来源删除、正文模式无内容的回归。缺正文时还应按真实 `read_mode` 说明，不能一律声称“仅读邮件头”。

### 问题 2：迁移新建缺少稳定身份，后续浏览产生重复记录

位置：[repair-browse-reviews.js:110](../server/scripts/repair-browse-reviews.js#L110)。

迁移直接 INSERT，仅保存部分字段，漏掉 `canonical_job_url`、`site_job_id`、`site_application_id`、JD 全文、字段来源和初始历史。新建分支也没有写 `events.application_id`。

隔离复现：旧浏览复核包含完整链接、岗位 ID 和 JD；迁移后岗位 ID、canonical URL、JD、事件关联均为空。再次提交同岗位浏览事件，正常业务匹配无法找到强身份，最终同一岗位出现 **2 条**。

验收库只读核查：迁移新建的 **5 条**记录都缺 canonical URL、site_job_id、JD；对应 **5 条**原事件的 application_id 也均为空。这里只能确认当前缺失，不能据此断言每条原始 JD 都存在；JD 原文丢失已在含原文的隔离样本中复现。

修复方向：通过统一的规范化创建/补全流程写入，保留稳定身份与来源、关联原事件，更新数据修订号；同时修复已迁移的 5 条，再验“迁移后重复浏览”和“迁移后详情补全”。现有脚本再次运行不处理已 resolved 项，单纯重复执行并不能修好它们。

### 问题 3：缺标题记录补全或再次浏览，仍会回到待确认

位置：[applications.js:466](../server/src/domain/applications.js#L466)。

新规则允许没有标题、仅有 URL 的记录入账，但原有标题冲突判断未适配这一行为。已有空字符串标题与后来取得的正常标题不同，被当成岗位身份冲突；已有空字符串与再次上报的 null 也不相等。

隔离复现：首次 URL-only 岗位成功建立 pending 记录；同 URL 补出标题，以及同 URL 再次上报空标题，均得到 `PAGE_CONTENT_IDENTITY_UNCERTAIN`，没有补全原记录。

修复方向：区分缺失值、字段补全与两个非空可信标题冲突，先统一空值表示。需要保护岗位身份，但不能把空值变为有值视作换岗。当前新增测试只断言首次入账或同一 client_event_id 重传，未覆盖新的浏览事件与后续补全。

### 问题 4：历史迁移可能跨网站错误合并相同数字岗位 ID

位置：[repair-browse-reviews.js:100](../server/scripts/repair-browse-reviews.js#L100)。

迁移用 `site_job_id 相等 OR job_url 相等` 查找第一条记录，没有按站点/域名约束岗位 ID，也没有排除同 URL 不同岗位 ID 的侧栏场景。正常入账处理器已有这些保护，迁移绕开了它们。

隔离复现：甲网站已有 ID 为 `audit-shared-id` 的岗位；乙网站的旧浏览复核也有这个 ID，但公司、标题和域名不同。迁移把乙网站事件关联到甲网站岗位，并关闭复核，没有为乙岗位建立记录。

修复方向：复用一致的身份匹配，候选唯一且身份无矛盾才合并；匹配不唯一时保留具体冲突。应审查已执行的 6 条合并。**本次没有证明真实这 6 条已错并，也没有修改或回滚它们。**

## 3. 完整需求中的既有缺口（并非本次提交新增）

### 问题 5：明确的投递成功邮件也不能自动记为已投递

位置：[mailParser.js:62](../server/src/domain/mailParser.js#L62)。

隔离输入：主题“【测试科技】投递成功通知”，正文“您的软件工程师岗位申请已成功提交，我们已收到您的简历。”

实际结果：`relevant=true, category='other', status=null`。当前分类器没有正常的 applied 映射，后续同步不会按投递成功进展处理。因而不能声称用户邮件能全面判断已投递，或只剩“阶段完成度”没做。

另外，`processMailEvent()` 在没有唯一候选时仍直接创建复核，包括没有浏览记录但邮件已明确公司、岗位和阶段的情况；跨笔试/面试阶段的 `STAGE_SPLIT_REQUIRED` 分支也仍存在。

### 阶段完成度与大模型

- 没有完成笔试/测评邀请与已完成的结构化处理；面试已有人工确认完成时间和详情展示，不能说项目完全没有面试完成能力，但从邮件/网页自动识别完成并一致呈现的闭环尚未完成。
- 页面大模型提取只有函数定义；没有调用方、实际提取链路与相应真实验收。邮件兜底不能代替完整的外接模型整理能力。
- BOSS、原生权限全流程和新版本真实站点复测仍未完成，与交付报告的“没做”一致。
