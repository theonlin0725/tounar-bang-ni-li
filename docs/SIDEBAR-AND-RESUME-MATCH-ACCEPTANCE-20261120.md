# TOUNAR 侧栏与简历匹配验收、自测和修复方案

复核基线为 `9bf7501`，对照 [开发需求单](SIDEBAR-AND-RESUME-MATCH-DEV-PROMPT-20261120.md) 与 [开发交付记录](SIDEBAR-AND-RESUME-MATCH-RESULT-20261120.md)。

**结论：侧栏和报告主流程可以开始自测，整体验收暂缓。** 侧栏的入口、视觉和移动端单列已落地。单岗位五段报告、历史与纠错已可操作。硬门槛误判和虚构优势可能直接影响用户的投递决策，需修复后再验收匹配结论。

## 需要修复的偏差

| 优先级 | 独立复现或代码证据 | 修复与验收标准 |
|---|---|---|
| **P0 硬性门槛及推荐互相矛盾** | JD 要求“上海线下办公”和“中国境内有效工作许可”。简历写“现居上海，仅接受远程办公；本人未取得任何工作许可”。模型漏报时，规则把两项都判成“满足”。另用模型返回没有用户证据的“不满足”，服务端仍把优先级改为“暂缓”，依据却仍写“没有阻断”，总体建议仍写“立即优先投递”。 | 把兜底规则用于发现 JD 条件，逐项区分强制要求、普通地点和加分项。用能够支持结论的对应用户证据核验“满足”和“不满足”。缺材料显示“信息不足”，冲突或待表态显示“需要用户确认”。明确冲突可判“不满足”。由同一份门槛结果生成顶部状态、依据、总体建议和六维门槛汇总。验收增加远程冲突、无许可、不同执照、不同类工作经验、软要求以及全部满足。不得出现相反投递指示。 [服务端门槛和兜底规则](../server/src/modules/career-ai/llm.js#L273) |
| **P0 优势和结论没有逐条证据** | 模型桩只返回 JD 引文“使用 SQL”，却给出“Tableau 项目增加营收 100 万”。服务端将该成果、维度“匹配”和“有证据的优势”照常输出。引文文本存在，仅能证明 JD 提到了 SQL。 | 让每条优势、明确缺口、用户事实与其引用绑定。核验来源类型和对应证据，肯定能力至少要有用户侧证据。无法核验的数字、技能和成果移出事实结论。保留“查阅过哪些材料、尚缺哪类证据”。顶层依据与简历优化、面试问题同样用已核验的证据。前端总结项可点回对应维度及引用，并正确标注“用户确认补充”。验收以仅 JD 引文、错领域引文及伪造收益为反例。 [维度清洗与总结生成](../server/src/modules/career-ai/llm.js#L414) [报告总结页面](../web/assets/js/views/career.js#L295) |
| **P1 导航选中态及移动端键盘** | 通过旧“看过没投”页签切换后，内容变了，侧栏仍把“投递台账”作为当前页。移动端打开抽屉后按 Tab 可跑到遮罩后的工作区。关闭态 CSS 仅平移抽屉，浏览器焦点仍需显式隔离。 | 让页签和侧栏从同一当前视图更新选中项、页标题和 `aria-current`。在移动端关闭时让抽屉退出键盘导航，打开时隔离背景并管理焦点。验收用鼠标与 Tab、Shift+Tab、Esc 分别经过旧页签、移动菜单、设置弹窗、返回及刷新。 [台账页签切换](../web/assets/js/views/ledger.js#L540) [移动端菜单](../web/assets/js/app.js#L222) |
| **P1 单岗选择和历史请求边界** | 代码只拉取“投递明细”和“看过没投”各前 100 条，普通选岗没有搜索或下一页。选不同历史报告时，回包只校验岗位，同一岗位的较早请求可以后到并覆盖最后的选择。 | 复用本人台账的搜索和分页，保留详情带入的选中项。历史请求按最新选择生效，失败或未完成报告显示独立状态。验收创建至少 101 条同视图岗位，搜索到后面的记录。用延迟模拟先点 A 再点 B，页面最终保持 B。 [岗位来源](../web/assets/js/views/career.js#L104) [历史报告加载](../web/assets/js/views/career.js#L520) |
| **P1 旧对比的触发行为变化** | 基线从台账选择两岗后进入即开始。交付版改成进入后还需点“开始对比”。两岗数据正常带入，少了一次自动请求，也多了一次用户操作。 | 保留“对比选中”这个显式动作的一次运行意图，或经产品确认采用两步。若恢复一步，在用户主动发起时调用一次，历史报告可恢复，刷新或直接访问旧深链不自动重跑。用请求计数同时覆盖从台账主动对比、旧链接和刷新。 [原对比验收覆盖](../tests/e2e/career-ai.mjs#L149) |
| **P2 报告行动与阅读** | 简历优化目前把各维度的文字拼进可编辑框，不能逐条定位至原简历段落和 JD。移动端页面上相近位置同时有多个“重新分析”。 | 优化建议逐条展示原简历引用、对应 JD 和建议文本，允许编辑及复制，原文由用户主动采纳。收拢重复的重跑入口，优先让用户看到双结论和门槛。验收实际点完五项行动并确认岗位、报告与证据都一致。 [简历优化操作](../web/assets/js/views/career.js#L388) |

先交付 P0 并补 API 反例测试，再修 P1 的入口、焦点与竞态，最后过完整视觉和操作回归。保留历史报告原文，修复后生成新结构版本或标明旧报告需重新分析，避免旧报告被解释成重新核验过。评分公式、权重和区间继续等产品确认。

## 你可以亲自操作的自测

### 准备隔离实例

在项目目录启动一个全新的临时库。默认测试账号为 `demo@tounar.local`，第二个普通账号为 `peer@tounar.local`。登录验证码写到这个实例的 outbox。运行真实匹配时需在本机为服务端配置原有模型网关 `AI_API_URL`、`AI_API_KEY`、`AI_MODEL`，本轮样例使用虚构简历及 JD。若模型尚未配置，可先测侧栏和未配置提示。PDF 要求服务端 Python 有 `pypdf`，也可直接粘贴测试简历。

```bash
cd /Users/mingenlin/orca/tounar-bang-ni-li
audit_dir="$(mktemp -d /tmp/tounar-sidebar-selftest.XXXXXX)"
printf '自测目录 %s\n' "$audit_dir"
DATA_DIR="$audit_dir" DB_PATH="$audit_dir/tounar.sqlite" \
  HOST=127.0.0.1 PORT=4324 APP_BASE_URL=http://127.0.0.1:4324 \
  MAIL_MODE=outbox ENABLE_SCHEDULER=false ENABLE_MAIL_SCHEDULER=false \
  ENABLE_REMINDER_SCHEDULER=false AUTO_INTAKE_ENABLED=false \
  CLOUD_PERSISTENCE_ENABLED=false CLOUD_LLM_ENABLED=false SHARE_CODE='' \
  ALLOWED_EMAILS=demo@tounar.local,peer@tounar.local ADMIN_EMAILS=demo@tounar.local \
  npm start
```

浏览器打开 `http://127.0.0.1:4324/`，用测试邮箱发送验证码。另开终端，在项目目录执行 `DATA_DIR="<打印的自测目录>" npm run otp:latest`。自测结束在启动终端按 Ctrl+C。

### 15–25 分钟主流程

1. **验导航。** 用管理员进台账，依次点左侧“看过没投”“待确认”“已归档”“匹配分析”“简历库”。核对右侧标题和侧栏高亮。点提醒设置与数据授权核对页签，再检查插件指引和邮件管理入口。换普通账号确认邮件管理入口隐藏，台账和报告各自隔离。用浏览器前进、后退、刷新和旧书签再走一次。
2. **造一条可测岗位。** 从台账点“归档线索”补录“验收科技 / 数据分析专员”，选“已投递”，填任一测试日期及独立岗位链接 `https://example.com/jobs/tounar-audit-01`。把下方 80 字 JD 填进摘要。保存后打开详情，记下岗位 ID、投递状态与日期。
3. **造一份缺证据的简历。** 去简历库粘贴下方简历并分析。回到刚才岗位详情，点“匹配分析”。预期自动选中该岗位，仅在点“开始匹配分析”后请求模型。报告可看见双结论、门槛、六维、总结和五项操作。核对没有自动生成数值分数。
4. **核对容易错的结论。** “现居上海”不能证明接受上海线下。“仅接受远程”和“未取得工作许可”要体现到门槛及建议中。简历没写 Tableau 经验或量化收益，报告不可当成已有。「硬门槛」「优势」或顶部建议出现任何一项反例，记录报告 ID、引文和截图即可判该条失败。
5. **验纠错。** 在技能或经历卡点“补充或纠错”，输入“我使用 Tableau 完成过一个商业分析 Dashboard”。先取消一次，确认没有落库。再次填写，选择“仅这个岗位”，确认后只出现一条补充。重跑得到新报告，新报告可以引用这项使用经历。切回旧报告核对原结论仍在。用另一个岗位验证该证据不串岗。
6. **验剩余动作和回归。** 点击简历优化、面试问题、查看岗位详情，核对真实输出与正确岗位。关闭详情能回到原报告。刷新报告页看历史，对照台账 ID、状态和投递日期。返回台账再补录一条“看过没投”，跨两个列表勾选，核对两岗对比和未投递推荐。缩到 390px，用键盘开菜单、Tab、Esc，然后用鼠标抽查遮罩关闭。

增补门槛样例时，复制出三个不同岗位或简历版本。一个省略许可信息，一个写明持有该许可且能接受上海线下，一个把 JD 的许可要求改成“具备相关证书优先”。分别观察“信息不足”“满足”和软要求是否被误列为硬门槛。可在确认修复前后复用同一套样例和报告核对表。
