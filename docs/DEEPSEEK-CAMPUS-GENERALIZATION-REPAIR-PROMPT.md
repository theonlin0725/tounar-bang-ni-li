# 开发任务 · 修复校招岗位自动识别的泛化问题

在「帮你理」当前工作区继续开发，以 0.2.10 的实现（394266d）和后续验收文档（8ae1733）为起点。完成可复现的诊断、核心代码修复和逐站复验。

## 用户要实现的体验

用户从 CSV 里的公司校招官网进入，正常操作站内导航或筛选，点击一个具体岗位。插件在获得必要的网站授权后，自动识别当前岗位、提取该岗位的 JD、交给 DeepSeek 整理，并将整理结果显示在台账「看过没投」。用户只需正常浏览岗位，无需打开插件或点「采集当前页」。

泛化目标是同一种页面结构换一家公司、不同招聘平台或不同打开方式也能工作。覆盖独立详情页、SPA 路由、列表内抽屉或左右分栏、新标签、共享招聘平台跳转。插件的输入范围是用户已经打开的单岗位详情，测试脚本可以模拟官网点击。保持现有网站授权、脱敏和隐私门槛。

## 现有证据和已知问题

- 公司清单为 `docs/recruitment-company-urls-20261118.csv`，当前矩阵为 `docs/campus-auto-detail-matrix-20261119.csv`。矩阵标「未验证」的 104 家原始 CSV 都没有详情样本。其中 102 家的旧入口巡检记录了 HTTP 200，但它们在现存 `.tmp/campus-live/*/results.jsonl` 中只有浏览器断开或新标签创建失败，无法据此判断网站上有没有岗位。另 2 家记录为未找到公开入口。
- 三次批量运行的浏览器失败条数分别为 113/119、122/126、127/128。同一公司可能出现在多次运行中。脚本启动一次浏览器，断开后还继续迭代并记异常。现有日志只证明批跑中断，崩溃原因需要另查。
- 百度、华为、哔哩哔哩等仅有历史入口记录，需要重新观察实际页面。旧 `.tmp/campus-audit/deep.jsonl` 给度小满留下详情候选，可先复核。共享平台出现的链接需要验证雇主和校招归属。字节历史上直链能自动整理，入口的项目筛选没有被脚本可靠操作。
- 已独立复现同一 JD 组件在详情路径可以自动触发，但在 `/jobs` 点击弹出详情且 URL 不变时，模型请求与 `job_viewed` 均为零。`extension/content/tracker.js` 的 `modelInput()` 在检查当前面板前拦截了列表路径。现有抽屉用例运行在 `/job/drawer`，没有覆盖这一问题。
- `tests/e2e/campus-auto-live.mjs` 按域名即可关联台账。Google、微软、安永的「前端通过」实际匹配到了同域其他岗位的 `job_discovered` 记录。成功断言也没有要求 `jd_text` 来自模型。已知正例是得物和微博。旧汇总里的 19 条包含直链和社招样本，跨域权限也由测试预授予。

## 实施顺序

### 1. 先修验收工具，恢复逐站诊断

- 让批跑可按公司或小批次执行、写检查点并续跑。浏览器断开时保留已完成记录，重建浏览器后有界重试。无法恢复时明确标出没执行的公司。区分网站超时、页面关闭和浏览器断开。测试配置从本地环境变量或显式配置读取，移除个人绝对路径，日志保留脱敏诊断信息。
- 导航根据可见的校招入口、下拉项目、岗位卡片和浏览器导航事件推进。记录每次实际操作及结果，明确检测列表、独立详情、新标签、URL 不变的抽屉和分栏。确认打开了一个有标题和 JD 的单岗详情再进入插件验收。点击失败、页面空壳、加载中、需要手动筛选、登录或验证码、确认无在招、详情失效分别记录，基于现场证据判断，不凭 HTTP 200 或固定等待时长推断。测试止于查看岗位详情。
- 建立严格的同岗断言。优先用站点岗位 ID 与租户，或规范化详情 URL，再核对点击标题和雇主。同 URL 面板用真实的岗位标识核对。事件必须发生在本次操作之后。要求同一条记录同时具有 `job_viewed`、`jd_text` 的模型成功来源（当前值为 `model_source_quote`）、真实前端渲染，以及可核对的岗位职责/要求。普通列表记录、同域其他岗位、原文兜底、社招、样本直链分别保留证据。旧的假阳性应有回归用例。
- 用得物和微博做验收工具的正对照，用字节历史直链作详情定位对照，并尝试从官网完成可见的校招项目筛选。验证浏览器中断后能继续跑下一家公司。

### 2. 修产品共性缺陷

1. **同页详情。** 在保护登录、简历、个人中心、投递表单等敏感路由的前提下，允许严格确认的可见单岗详情面板覆盖普通列表路由的拦截。复用现有面板探测、可信选择器和 JobPosting。必须验证「同一列表 URL，打开前零模型请求和零浏览入账，打开后只采当前岗位，关闭后停止」。并排列表、多岗位推荐、隐藏面板、公告不能进入模型正文。支持其他站点采用的结构时，先用真实样本证明现有逻辑哪里失效，再优先修共性规则或平台模板。
2. **岗位身份和模型结果。** 验收至少包含同 URL 两个不同岗位、同名不同岗位、快速 A→B、刷新重进、模型暂时失败后恢复。快速切岗测试必须先等到 A 的请求已发出，再切 B。检查真实服务端和台账，确认不会因同一个 URL 串岗或重复建账，B 能得到正确 JD。规则兜底可以保留，但不能冒充模型整理成功，也不能因兜底阻止后来成功的模型结果进入台账。
3. **跨域授权。** 选一个真实的官网跳招聘平台案例，从只授权入口开始。确认未授权详情零模型请求，用户能看到实际需要授权的域名。用户用现有授权入口同意后，回到该岗位按正常自动路径拿到模型 JD。使用发布版权限配置和真实 Chrome 授权操作验收。预授权测试用于验证识别能力。共享 ATS 核对租户和页面实际雇主。

### 3. 按清单验证泛化并交付

- 先从未验证公司中选有历史候选的度小满，再覆盖 SPA、自建银行或券商站、共享 ATS。拿一组真实失败样本定位根因，每类修复后用另一家未用于写规则的公司验证，继续分批复跑剩余清单。若某站需要用户登录或验证码，记录可复现的阻塞，不代替用户完成验证。
- 为 130 行逐一记录实测进度或具体阻塞。至少保留 CSV 行号、入口、实际点击步骤、最终域名、详情 URL 或面板标识、岗位及雇主、校招证据、授权状态、模型来源、事件与台账 ID、前端核验和失败阶段。过往结果保留原样，修前修后用相同样本比较。
- 报告三组分子和分母。第一组是「从官网实际点击并完整走通的校招公司数 / 130」。第二组是「已打开且确认有效并获授权的校招详情中，自动整理并显示的样本数 / 该类样本总数」。第三组是「真实跨域补授权后走通的案例数 / 实测案例数」。另报未跑到的行数、直链定位结果、社招结果及真实外部阻塞。旧入口探测、测试异常和其他岗位的前端记录均不能计入成功。
- 交付核心修复、可执行的本地验收命令、关键回归用例、逐公司矩阵和结果摘要。保留得物、微博及旧插件、权限、JD 模型、前端回归。以真实用户路径和同岗位证据判断交付，不靠增加域名数量或硬编码样本提高数字。
