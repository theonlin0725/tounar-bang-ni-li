# 简历库新增「简历改写」模块开发方案（含可行性评估与 Word 导出）

**日期**：2026-11-22
**基线分支**：`tounar-1.1.0`（在 `1.1.0` 线上迭代，**绝不改动已封板的 `tounar-1.0.0` / `v1.0.0`**）
**核心目标**：在「简历库」页面新增独立的「简历改写」工作台——支持从「投递明细」或「看过没投」任选目标岗位、选择原始简历版本、执行 9 步结构化对齐改写、以**左右对照高亮可编辑**方式审阅修改，并在用户确认后按 `原简历名_岗位名` 保存为新简历版本且导出排版整洁的可编辑 Word（`.docx`）文件。

## 1. 技术可行性评估结论

| 需求点 | 可行性 | 评估说明与落地策略 |
|---|---|---|
| 从「投递明细」与「看过没投」选岗位 + 选择简历版本 + 联动求职画像 | ✅ **完全可行** | 复用 `/api/v1/ledger`、`resumes` 表及 `user_profiles` 表，与 AI 助手共享二级岗位选择器组件 |
| 9 步结构化改写工作流 + 4 级事实对齐护栏（禁止编造无证据内容） | ✅ **完全可行** | 基于现有 `server/src/modules/career-ai/rewrite.js` 升级为完整 9 步结构化 JSON 契约 + 服务端原文逐字校验 |
| 左右对照呈现（左原简历排版 / 右高亮修改、点击可直接编辑） | ✅ **完全可行** | 前端纯 Vanilla JS 实现结构化段落对照视图，支持高亮批注、点击行内编辑、接受/撤销单段修改与补充事实合入 |
| 保存为新版本（默认 `原简历名_岗位名`，可重命名，不覆盖原简历） | ✅ **完全可行** | 直接复用 `resumes` 表的 `parent_resume_id`、`target_application_id`、`rewrite_summary_json` 字段 |
| **按原 PDF 排版格式生成 Word（`.docx`）** | ⚠️ **需采用双轨务实方案** | **诚实技术判断**：纯 Node.js 在不依赖商业排版引擎的前提下，无法对任意复杂设计型 PDF（多栏、矢量图表、绝对定位文本框）做 100% 像素级逆向还原再替换文字。**推荐落地方案**：① 若原简历上传的是 `.docx`，保留原 `.docx` 模板样式做 XML 段落级替换（高保真还原）；② 若原简历是 `.pdf`，在解析阶段提取**模块顺序、标题层级、字号比例、页边距与主色调**，改写确认后使用标准化 `.docx` 生成器（如 `docx` 库或内置 OOXML 生成器）输出**结构与风格对齐原简历、ATS 友好的专业可编辑 Word 文档**，并在界面诚实提示“已按原简历结构生成可编辑 Word”。 |

## 2. 页面入口与交互设计（对齐图 3 与图 5）

### 2.1 「简历库」二级导航入口（`web/assets/js/views/career.js`）
- 在左侧「简历库」（`/?panel=career&section=resume`）顶部增加清晰的二级页签：
  - **`我的简历`**（保持现有上传、解析、多版本切换、设为当前、手动编辑功能 100% 不变）；
  - **`简历改写`**（新增工作台，支持从 AI 助手、岗位详情抽屉或匹配报告通过 `/?panel=career&section=rewrite&app=<id>` 一键跳转并预选岗位）。

### 2.2 第一步：改写配置区（对齐图 3 与图 5）

![图3：简历改写前置上下文卡片（目标岗位、简历版本、求职画像、JD 信息）](assets/v1.1.0-ref/fig3-profile-and-rewrite-context.png)

![图5：选择简历版本弹窗参考设计](assets/v1.1.0-ref/fig5-resume-version-selector.png)

顶部 4 张信息卡（布局对齐图 3）：
1. **目标岗位卡**：展示已选岗位 `岗位名 · 公司名 · 城市` + `[更换岗位]` 按钮；点击弹出与 AI 助手共用的**二级岗位选择器**（「投递明细」/「看过没投」→ 具体岗位列表，支持搜索与下滑加载）。
2. **简历版本卡**：展示当前预选简历（如 `主简历 v3（默认预选）`）+ `[更换简历]` 按钮；点击弹出对齐**图 5** 的单选卡片弹窗（提示 `用于本次优化的简历将作为新版本保存，不覆盖原文件`，列出所有简历版本与更新时间，底部 `[取消]` `[确认选择]`）。
3. **求职画像卡**：展示已确认的求职画像摘要（如 `已确认画像 · 产品 / 数据分析方向`）+ `[编辑画像]` 按钮（未建立时提示“去 AI 助手快速建立”或手动填写）。
4. **JD 信息卡**：展示目标岗位 JD 状态（`已加载目标岗位完整 JD（岗位职责 + 任职要求）`）；若该岗位缺少 JD，给出明确提示与一键「补充 JD」入口，避免空跑模型。
5. 可选补充输入框（如“重点突出数据分析与 AI 项目经历”）+ 主按钮 **`[开始定向改写]`**。

### 2.3 第二步：左右对照审阅与在线编辑工作台

改写完成后进入**左右分栏对照视图**（窄屏自动切换为上下对照或切换 Tab）：

- **左栏：原始简历（只读，结构化排版）**
  - 按解析出的模块（基本信息 / 教育背景 / 实习与工作经历 / 项目经历 / 技能与证书）清晰排版，带模块标题与条目圆点，与右栏段落**一一对齐联动滚动**。
- **右栏：AI 改写后的完整简历（高亮 + 可点击编辑）**
  - **高亮展示修改片段**：所有被 AI 优化表达的文本以柔和浅青/浅黄底色高亮；点击或悬停高亮块时，弹出紧凑批注展示「改动原因」「对应的 JD 关键词依据」以及 `[还原此段]` 按钮；
  - **点击直接编辑**：用户点击右栏任意段落或高亮片段即可进入行内编辑态（`contenteditable` 或自动增高文本域），实时保存草稿；
  - **「待补充事实」提示区**：对工作流识别出的 `needs_user_fact`（需要用户补充真实数据/经历细节）条目，单独展示在右栏对应模块下方或右侧抽屉，用户补充真实事实后可一键插入正文，**绝不由 AI 替用户编造数字或经历**。
- **底部：简历改写报告折叠区**
  - 展示本次提取的 JD 核心关键词覆盖率、能力差距清单、4 类对齐统计（优化了 N 段、待补充 M 项、拦截无证据项 K 项）。

### 2.4 第三步：确认保存新版本与导出 Word（`.docx`）

- 点击底部主按钮 **`[确认并生成 Word]`**，弹出轻量确认框：
  - **新简历名称输入框**：默认预填 **`原简历名_岗位名`**（自动去除 `.pdf/.docx` 后缀与非法路径字符，如 `林铭恩简历_数字化产品经理`），允许用户自由重命名；
  - 勾选框：`保存后设为当前主简历`（默认不勾选，由用户决定）；
  - 按钮：`[取消]` `[确认保存并下载 Word]`。
- 执行结果：
  1. 在 `resumes` 表新增一条独立简历版本（写入 `parent_resume_id`、`target_application_id`、`rewrite_summary_json`、`docx_path`），**原简历保持完全不变**；
  2. 生成对应 `.docx` 文件并自动触发浏览器下载，同时在「我的简历」列表中为该版本提供随时再次下载 Word 的按钮。

## 3. 九步后端改写工作流与四级事实对齐护栏

### 3.1 严格九步工作流（`server/src/modules/career-ai/rewrite.js`）

将单次粗粒度改写拆解为结构化 9 步流水线（支持后端状态进度回传，避免前端干等）：
1. **读取目标岗位完整 JD**：校验 `jd_text || jd_summary` 充足；
2. **读取所选简历版本**：读取原始全文、解析结构及原文件类型（`pdf` / `docx` / `text`）与样式元数据；
3. **提取 JD 关键词与能力要求**：输出硬技能、软能力、业务场景与高频词表；
4. **解析简历中的技能、经历和项目**：按模块拆分为带稳定 `block_id` 的段落列表；
5. **对齐 JD 与简历内容**：建立 `block_id ↔ JD 要求` 的映射关系；
6. **识别能力差距**：列出简历未覆盖或覆盖薄弱的 JD 要求；
7. **生成逐段修改建议（强制四级分类）**：每条映射必须落入下表 4 类之一，服务端做二次强校验：

| 对齐类型（`alignment_type`） | 含义 | 系统处理方式 |
|---|---|---|
| `supported_optimize` | **已明确存在的经历** | 优化措辞、突出行动与已有量化结果、对齐 JD 关键词，高亮写入右栏改写稿 |
| `improvable` | **可以优化的经历** | 提供 1–2 个改写建议版本供用户点选或微调后写入 |
| `needs_user_fact` | **需要用户补充事实** | **不直接捏造**，进入「待补充状态」卡片提示用户补充具体指标/职责 |
| `unsupported_blocked` | **当前没有证据支持的内容** | **硬拦截，不允许写入改写稿**，仅在改写报告的能力差距栏提醒用户 |

8. **生成岗位专属简历草稿**：仅由原简历事实 + `supported_optimize` + 用户采纳项拼接为结构化模块草稿（严禁包含任何 `unsupported_blocked` 内容）；
9. **生成简历改写报告**：汇总 JD 关键词命中率、能力差距、四级分类明细与风险提示，持久化到 `resume_rewrite_sessions` / `ai_reports`。

### 3.2 Word（`.docx`）排版导出引擎（`server/src/modules/career-ai/docx-exporter.js`）

- **双轨生成策略**：
  1. **原文件为 `.docx`**：读取原 `.docx` 模板样式（字体、标题样式、页边距、行距、配色），按模块/段落替换确认后的文本并输出新 `.docx`；
  2. **原文件为 `.pdf` 或纯文本**：
     - 在解析原 PDF 时额外抽取轻量版式特征（`layout_meta_json`：模块顺序、是否含双栏、主标题字号/颜色倾向、页边距估计）；
     - 导出时使用标准化 OOXML `.docx` 生成器（优先零/轻依赖方案或引入 `docx` 包，须在实施前确认依赖许可与体积），采用**微软雅黑 / 思源黑体、清晰模块分割线、统一页边距与项目符号**生成干净、专业、可直接投递和在 Word/WPS 中二次微调的 `.docx` 文件。
- **文件存储与安全**：
  - 生成的 `.docx` 仅保存在当前实例 `DATA_DIR/resumes/<owner_id>/<resume_id>.docx`（权限 `0600`，严格位于 `.gitignore` 范围，绝不入库 Git）；
  - 下载接口 `GET /api/v1/resumes/:id/export.docx` 强校验登录态与 `owner_id` 归属权，返回 `Content-Disposition: attachment` 且文件名采用用户确认的 `原简历名_岗位名.docx`。

## 4. 增量数据表与 API 契约

### 4.1 增量表与字段（仅增不改，向后兼容）
- 新增 **`resume_rewrite_drafts`** 表：保存用户正在审阅/编辑的改写草稿（`id`、`owner_id`、`source_resume_id`、`application_id`、`status`、`jd_analysis_json`、`alignment_json`、`blocks_json`、`report_json`、`proposed_name`、`created_at`、`updated_at`），防止刷新页面丢失编辑进度。
- `resumes` 表增量补充：`export_docx_path TEXT`、`layout_meta_json TEXT`（连同既有 `parent_resume_id`、`target_application_id`、`rewrite_summary_json`）。

### 4.2 新增 API 路由
| 方法与路径 | 说明 |
|---|---|
| `POST /api/v1/resumes/rewrite/drafts` | 触发 9 步改写工作流（入参 `resume_id`、`application_id`、`requirements`），支持异步轮询或 SSE 进度，返回草稿 ID 与结构化结果 |
| `GET /api/v1/resumes/rewrite/drafts/:id` | 获取改写草稿（原简历结构化块、改写高亮块、4 类对齐明细、待补充项、改写报告） |
| `PATCH /api/v1/resumes/rewrite/drafts/:id` | 实时保存用户在右栏对任意段落的手动编辑、待补充事实输入或自定义名称 |
| `POST /api/v1/resumes/rewrite/drafts/:id/confirm` | 确认保存为新简历版本（默认 `原简历名_岗位名`，支持传入 `name`、`set_current`）并生成 `.docx` |
| `GET /api/v1/resumes/:id/export.docx` | 安全下载指定简历版本生成的 Word 文档（校验 `owner_id`） |
