### 本机管理员自测登录（后备通道）

这是为了避免 SMTP 故障时连管理员也进不去；它不是通用后门，默认关闭。

- `npm run mail:selftest` 只为固定自测副本设置 `ENABLE_SELFTEST_LOGIN=true`；`npm start` 和生产启动不设置。
- 只同时满足以下条件才回显验证码：`APP_ENV=development`、`APP_BASE_URL` 是 `http://127.0.0.1` 或 `http://localhost`、请求来自回环地址、邮箱同时在 `ADMIN_EMAILS` 和 `ALLOWED_EMAILS` 中。
- 在登录页输入管理员邮箱，点击「获取验证码」。页面会显示并自动填入 6 位验证码，**不发送邮件**；再点「验证登录」即可进入。普通用户、非本机请求、生产域名或开关关闭时都不会回显，仍走正常发信流程。
- 每次仍受验证码限流和尝试次数限制；审计表记录 `auth.selftest_otp_issued`（不记录验证码）。验证码仍写入 `otp_challenges`，登录后是正常管理员会话。
- 关闭：`npm run mail:selftest:stop`，从启动环境移除 `ENABLE_SELFTEST_LOGIN` 或设为 `false`，再启动。生产环境禁止开启。

## 二、最容易跑通的完整路径（约 10 分钟）

以下路径验证：**你提交台账信息 → 产生真实未消费的进展通知 → 候选筛选 → 当前模板渲染 → SMTP → 你在收件箱确认**。测试按钮是管理员手动触发，它跳过定时时间，但沿用正式摘要的筛选、卡片、邮件组装和发信代码。它不证明每日 08:00 的调度已执行。

### 第 1 步：登录并确认环境

打开台账，退出不具备管理员权限的账号，用启动器打印的管理员邮箱获取验证码。若页面出现「本机管理员自测模式」并自动填入验证码，直接点击「验证登录」，不会发送邮件；否则会真实发送登录邮件，去该邮箱收件箱读取验证码后登录。

预期：进入台账，顶栏出现「邮件测试与模板」。进入面板，顶部显示「SMTP 真实发信」以及发件人；如果显示 outbox，应停止并使用 `npm run mail:selftest` 启动。自测验证码只用于本机管理员登录，不代替后面的真实发信验收。

### 第 2 步：开启进展提醒

返回台账，点击顶栏「提醒设置」；「接收哪些提醒」选择「全部」或「仅状态变化」，保存。不要选择全部关闭或仅回看。

预期：保存成功，重新打开设置仍保留该选项。这里不会立即发摘要邮件。

### 第 3 步：亲自提交测试数据

台账点击「+ 归档线索」（旁边提示“补录漏采岗位”，这是手动补录入口），填写：

| 页面字段 | 示例 |
|---|---|
| 公司 | 自测科技-1030-A |
| 岗位 | 产品经理-邮件通路A |
| 已正式申请 | 勾选 |
| 状态 | 已投递 |
| 投递日期 | 测试当天，如 2026-10-30 |
| JD 摘要 | 负责用户研究和产品方案，仅用于邮件通路自测。 |
| 岗位链接 | https://example.com/jobs/mail-selftest-1030-a |
| 城市 | 上海 |
| 招聘批次 | 自测批次 |

点击「保存到台账」。这是创建业务记录，不是立即发邮件。

预期：提示“已保存到台账”；详情中的公司、岗位、日期、JD、链接与输入一致。记录会产生一条手动补录的进展通知，等待摘要发送。投递日期请用当天，早于 30 天的进展可能不进入近期进展候选。重复测试另建记录时要换岗位链接，避免去重冲突。

### 第 4 步：预览真实业务邮件

点击「邮件测试与模板」，测试模式选择「B · 测试真实业务触发通路」。收件人选择你现在能查看的测试邮箱；从记录下拉框中选择刚才的「自测科技-1030-A · 产品经理-邮件通路A」。如果没出现，点击「刷新台账记录」。

点击「预览已保存版本／业务内容」。

预期：出现主题、模板版本、HTML 预览、纯文本正文、实际渲染 HTML 源码。主题以「【自测·业务通路】」开头，包含公司／岗位；正文“一、有进展”包含手动补录说明、发生日期、官网链接和台账详情链接。默认只显示核心信息，城市和 JD 可按后面的模板修改步骤加入。

预览不会发送、不会消费通知，也不会更新最近回看时间。预览中的回看确认链接是占位；实际发信生成真正链接。不要在预览 iframe 内执行链接操作。

### 第 5 步：你亲自触发真实发送

确认收件人，点击「发送到所选测试邮箱」。**这个按钮才会把预览对应的已保存模板交给 SMTP。**页面发送期间禁用按钮；同一次请求重试会复用触发记录。每位管理员每分钟最多 5 次试发。

预期：下方出现一条「业务通路」触发记录，显示所选台账 ID、测试收件人、批次 ID、使用的模板版本、邮件 ID，以及「SMTP 已受理，请检查收件箱」。发送过程中可以用「刷新记录」查询状态。

### 第 6 步：在收件箱完成最后一跳

去选定邮箱查找主题带「【自测·业务通路】」及刚才公司／岗位的邮件，也检查垃圾邮件、推广／订阅分类。

核对主题、公司、岗位、日期、说明和链接；点击「在台账里查看」，应打开这条记录。如果邮箱在手机或另一台电脑，`127.0.0.1` 指的是那个设备，不是你的 Mac；本次请在运行项目的同一台 Mac 浏览器中验证链接。

**通过条件：**产品内确有你提交的记录；业务触发记录及发送记录可对应；版本号正确；收件箱实际收到对应邮件；内容及详情链接正确。仅看到 accepted 不算收件箱验收通过。

这个测试使用独立批次，不消耗当天正式摘要和回看频控，因此可以在改模板后反复运行。它只处理所选的本人记录，不混入别人的记录或其他待确认摘要。待确认摘要的版式可以用对应模板试发；真实招聘邮件读取与分类是另外的 IMAP 验收范围。

## 四、模板查看、修改与再次发信确认

共有五种可管理模板：登录验证码、提醒摘要（整封）、进展卡片、回看卡片、待确认卡片。摘要中的三类卡片分别渲染后放入整封模板；验证码独立发送。

所有模板在面板右侧选择；可查看主题、纯文本、HTML、变量说明、系统示例、当前版本和历史版本。默认源文件是 `server/src/modules/mail-push/template-defaults.js`；保存后以当前副本 SQLite 的 `mail_template_versions` 表为准，修改不再需要直接编辑代码。

### 推荐修改实验：加入城市、JD 和可识别的版本文案

1. 选择「进展卡片」。先记下当前版本，如 v1。
2. 在纯文本末尾加入：

   ```text
   城市：{{location}}
   JD：{{jd_summary}}
   模板验证文案B
   ```

3. 在 HTML 末尾加入：

   ```html
   <p>城市：{{location}}</p>
   <p>JD：{{jd_summary}}</p>
   <p style="color:#17594c">模板验证文案B</p>
   ```

4. 点击「预览编辑中的草稿（不发送）」，查看效果和错误。若处于业务模式，先切回 A 模式预览草稿。
5. 点击「保存并启用新版本」。预期版本升为 v2；保存时也会用下方当前示例变量验证约束。修改立即影响本环境后续生成的邮件，不追改已经发出的邮件，不需重启。
6. 切回 B 模式，选之前创建的业务记录，重新预览并发送。
7. 收件箱中第二封邮件应包含“城市：上海”、你的 JD 和“模板验证文案B”；发送记录中的 `progress_item` 应为 v2。这一步同时证明修改后的卡片进入真实业务摘要。
8. 修改整封主题时选择「提醒摘要（整封邮件）」；卡片的“主题”仅用于卡片单独试发，不决定整封摘要主题。

整封模板中的页眉、页脚、推送时间文案和整体排版也可直接编辑；`{{pushed_at}}` 为实际推送时间（UTC），`{{settings_url}}`、`{{reviews_url}}`、`{{ledger_url}}` 为系统入口。HTML 支持段落、标题、链接、表格、列表等展示标签和安全的内联样式。文本变量自动转义；只有变量表标注的系统 HTML 片段允许三花括号。脚本、事件属性、表单、图片和 CSS URL 会被拒绝。复杂邮件客户端兼容布局、增加新变量或改变业务筛选逻辑需要改代码。

### 仅验证模板和邮箱（A 模式）

选择 A，选择模板，展开「测试变量与字段说明」直接编辑示例变量，选择测试邮箱，先预览已保存版本，再发送。主题固定加「【自测·模板试发】」。示例验证码 123456 不具有登录效力。提醒摘要的 body_* 在 A 模式由你填写，**不是业务记录**，所以 A 成功不能证明 B 成功。

### 恢复历史版本

在「版本历史」选 v1，点「查看所选版本」可以把旧内容载入编辑器，但尚未改变当前生效版本。点「恢复所选版本并启用」会将旧内容保存成一个新的版本（如 v3），保留修改轨迹。重新预览再发送，核对记录显示 v3、邮件不再包含版本文案B。恢复不会撤回或修改已经收到的邮件。

恢复会使用该历史版本保存的示例变量并执行同样的校验；示例变量也随版本保存。多个页面同时编辑时，过期版本不能覆盖新版本，刷新后再修改。

## 五、约束配置与可直接执行的异常实验

管理员可在表单配置：必填变量、可选变量缺失时阻止／留空／替代文案、每个变量最大字数、主题／纯文本／HTML 最大长度、必须出现的固定文案、禁止出现的内容。字数按 Unicode 字符计数；HTML 限制按源码计数。固定／禁止文案在渲染后的主题和正文合并检查，禁止词忽略大小写，均为字面匹配而非正则表达式，不是法律合规或完整语义过滤器。

系统强制、网页不能关闭：核心验证码和业务入口变量、安全 HTML、主题禁止换行、管理员权限、测试收件人白名单、频率上限、使用已保存版本及版本冲突保护。新增字段来源、循环结构、复杂业务规则、链接安全策略或收件人权限模型需要代码修改。

推荐在「进展卡片」上实验；保存前先让示例数据符合规则：

| 实验 | 配置与测试数据 | 应看到的结果 |
|---|---|---|
| 必填 | 勾选 `location` 必填，示例先填“上海”后保存；再清空示例城市并预览 | 明确提示必填变量 location 缺失；不发送 |
| 真正缺失 | 未勾选 location 必填，且正文引用 `{{location}}`；在“删除变量”中选择 location | missing=error 时阻止；empty 时该位置为空；fallback 时显示你配置的“待补充” |
| 变量长度 | 设置 job_title 最多 10 字，示例“产品经理”保存成功；改为“产品经理产品经理产品经理”并预览 | 提示 job_title 超过 10 字，请缩短 |
| 固定文案 | 在正文加入“仅用于自测”，固定文案列表也加同一行，然后保存；尝试删除正文里的这句话 | 草稿预览和保存均被阻止，说明缺少固定文案 |
| 禁止词 | 禁止内容列表加“保证录用”，用正常示例保存；把 description 改为“保证录用”后预览 | 指明含禁止内容“保证录用”，拒绝发送 |
| 总长度 | 记录当前主题长度上限，将其改成 5 并保存 | 保存失败并指出 subject 超长；改回 180 后可保存 |
| 核心字段保护 | 在验证码模板删除 code 或 ttl_minutes | 保存／预览被拦截，要求保留验证码和有效期 |
| 变量拼错 | 写入 `{{job_titel}}` | 指出未知变量，按变量表修正 |
| 非法 HTML | HTML 中加入 `<script>alert(1)</script>` | 拦截非法 HTML，页面不会执行脚本 |
| 无提醒候选 | 关闭提醒，或选尚无近期进展／未到期的记录，进行 B 预览 | 提示没有符合条件的候选；不发送；恢复提醒并新增当天测试记录再测 |
| 预览后改模板 | 两个标签页，A 已预览，B 保存新版本，再在 A 发送 | 提示版本变化，要求重新预览；不发送过期内容 |
| 未授权账号 | 普通白名单账号登录后访问管理入口 | 显示仅管理员可使用；无法取模板和发送记录 |
| 非测试收件人 | 页面只能从指定名单选；接口绕过下拉尝试其他地址 | 拒绝发送，错误为 TEST_RECIPIENT_FORBIDDEN |

错误会出现在页面上方并标明字段、规则和修改办法，输入内容保留。正文版本未保存时只能预览草稿；必须保存并预览已保存版本后才能发送。更换模板、记录、变量或收件人后，需要重新预览。

## 六、状态与故障定位

| 面板状态／现象 | 含义与下一步 |
|---|---|
| 发送中 | SMTP 请求进行中；点击刷新记录。持续超过两分钟的中断记录保守标为送达未知 |
| SMTP 已受理（accepted） | SMTP 明确接受了目标收件人；查看收件箱、垃圾邮件、服务商投递策略。不是已读或保证到达 |
| 仅写本地（outbox_written） | 未真实发信；检查是否用了专用 SMTP 启动器 |
| failed / EAUTH | 邮箱或授权码错误；只在本机 .env 修正，重启服务，再重新预览发送 |
| failed / ECONNECTION 或 EDNS | 检查网络、SMTP 主机、465／587 端口；不要把本地网页端口当成 SMTP 端口 |
| failed / RECIPIENT_REJECTED、EENVELOPE | 服务商未接受目标收件人或发件身份，检查邮箱和服务商限制 |
| delivery_unknown | 超时、连接中断或进程被中断；先查收件箱，确认后再决定重发，可能已经送达 |
| TEMPLATE_INVALID | 模板或实际业务数据违反约束；按具体字段修正，重新预览 |
| skipped_empty / NO_CANDIDATES | 当前记录没有可发送内容；开启全部／状态变化提醒并提交当天的新记录 |
| RATE_LIMITED | 每分钟最多 5 次，等待后重新预览再试 |
| VERSION_CONFLICT | 模板或台账在预览后变化，重新预览 |
| 127.0.0.1 拒绝连接 | 在项目目录运行 `npm run mail:selftest`；端口被别的服务占用时不会擅自关闭它 |

页面最下方是触发记录、邮件投递记录、业务批次状态。触发记录关联台账、批次、模板版本和服务商邮件 ID；失败原因用安全说明，不回显 SMTP 授权码。更底层日志位于 `data/mail-selftest/server.log`；排查时记录触发 ID 和时间，不要分享私密数据文件。

当前没有服务商回执 Webhook、退信解析或已读跟踪，因此不会把“SMTP 受理”显示为“收件箱收到”。请手工记录最终收件时间及主题。普通正式摘要仍按业务规则每日批次去重；B 模式的独立测试批次专门用于重复验证，不改变正式通知消费状态。

## 八、实现位置与能力边界

- 管理页面：`web/assets/js/views/mail-admin.js`；入口由 `/api/v1/me` 的管理员标识控制，所有管理 API 再次校验管理员身份。
- 管理接口和测试流程：`server/src/modules/mail-push/admin.js`。
- 默认模板：`server/src/modules/mail-push/template-defaults.js`；渲染、校验、版本：`templates.js`。
- 正式摘要候选和共享组装：`reminders.js`；SMTP 和投递审计：`mailer.js`。
- 启停入口：`server/scripts/mail-selftest.js`。
- 各环境的模板版本独立存库。自测副本中的修改不会自动同步原库或线上；迁移到正式环境需要另行审阅与发布。

本次准备仅进行隔离 outbox 功能回归和页面可用性检查；真实 SMTP 的提交、收件箱到达及客户端排版由你按上述步骤完成。不要将自动回归通过视为真实发信验收通过。
