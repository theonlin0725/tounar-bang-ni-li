## 二、已知的代码现状，不要重复误判

1. 当前只有腾讯部分详情页拥有已验证的高分适配规则；仅增加 `hosts` 或 URL 正则，不等于完成一个网站适配。
2. 当前“授权当前标签页站点”主要是申请源权限并重建动态 content script，没有对已打开的当前标签页立即注入、立即探测，也没有当前页识别结果展示。
3. 当前识别以岗位详情为主；列表/搜索页不能批量生成正式申请或浏览事件。
4. 当前正式上传字段中的 `jd_summary` 以不超过 80 个中文字符为展示目标，不能在本任务中偷偷改成默认上传完整 JD。
5. 当前没有持久化的“站点布局档案/学习结果”存储。
6. 现有测试构建会额外添加静态注入和本地主机权限，不能据此证明生产环境的“用户授权当前页后立即识别”已通过。
7. 现有 `server/src/cloud/llm.js` 的能力不等于站点布局学习，不得把简单公司/岗位抽取包装成“已学会全网网页”。

## 三、一期总目标

把插件升级为：

**用户明确授权当前站点 → 当前页无需刷新即开始识别 → 判断页面类型 → 提取岗位字段 → 当前端预览/现有前端展示 → 可靠布局可记忆复用 → 网站改版可诊断并回退。**

一期同时覆盖两类能力：

- 首批种子网站：建立真实 DOM/页面证据驱动的适配和回归样本。
- 未见过但由用户授权的招聘网站：通过通用识别和可验证的站点档案实现兼容，不宣称无条件支持全网。

## 四、硬边界，不能为了“抓取成功”突破

1. 只处理用户已打开且已授权的 HTTP/HTTPS 页面；用户授权不等于平台许可。
2. 不自动打开详情页、不自动翻页、不自动滚动遍历、不批量展开、不发隐藏查询请求、不做服务器代抓。
3. 用户手动导航、滚动或翻页后，可以处理当前已渲染且允许采集的内容。
4. 不绕过登录、验证码、风控、字体混淆、跨域限制或其他反自动化机制；遇到时显示明确状态和人工处理提示。
5. 不读取或上传 Cookie、请求头、账号密码、简历、联系方式、身份证、附件、输入框值和完整 HTML。
6. 不自动点击投递，不把申请按钮、表单点击或 HTTP 200 当作投递成功。
7. 不新增常驻 `<all_urls>` 或静态全站 content script；继续采用用户显式授权的最小源权限。
8. 跨到新的官方 ATS/招聘域名时重新判断权限；不得因为“属于同一家公司”就自动获得新源访问权。
9. 保持现有 C1 事件顶层契约和 `processPluginEvent()` 统一入账链，不另写一套申请去重/状态处理器。
10. 列表预览与正式申请入账必须分开：列表页可预览，但不批量创建 `job_viewed`、正式申请或投递状态。
11. 正式上传仍使用现有字段和 `jd_summary ≤80 字`；完整 JD 只允许用于当前页本地预览。若确需完整 JD 入库，单独列出契约和隐私变更，不在本任务中暗中实施。
12. 不用空成功、假字段、假测试或删掉失败样本的方式宣称“支持”。

## 五、工作包 A：修复“授权当前页后没有反应”

1. 保留 Chrome 对 `chrome.permissions.request()` 用户手势的要求。若权限申请必须留在 popup 的真实点击链路，就不要为了架构整洁强行移入 service worker。
2. 将授权后的动态注册、当前页注入、状态查询和撤权流程整理成可复用、可测试的模块；popup 负责交互，service worker 负责可集中管理的生命周期。
3. 授权成功后：
   - 保留后续导航所需的动态 content script 注册；
   - 对触发操作的当前 `tabId` 立即注入现有适配器与 tracker；
   - 立即触发一次页面探测，不要求用户手动刷新。
4. 动态脚本只管理自己的固定 ID，不得注销其他脚本。
5. 注入和初始化必须幂等：重复点击授权、动态注册与立即注入同时发生、SPA 重入时，不得重复绑定监听器或重复产生事件。
6. 增加明确的消息协议，名称可按项目风格调整，例如：
   - `grant_current_origin`
   - `probe_current_page`
   - `get_current_page_status`
   - `revoke_origin`
   - `forget_site_profile`
7. 探测结果至少返回：
   - `status`
   - `origin`
   - `page_type`
   - `adapter_key`
   - `extraction_mode`
   - `profile_version`
   - `fields` 或当前列表预览 `items`
   - `field_confidence` / `field_sources`
   - `missing_fields`
   - `diagnostic_code`
   - `elapsed_ms`
8. 页面类型至少区分：
   - `job_list`
   - `job_detail`
   - `application_form`
   - `application_status`
   - `non_job`
   - `login_or_blocked`
   - `unknown`
9. 增加用户主动纠偏入口：“这是招聘页，重新识别”。用户指定后应启动通用提取，但低把握结果仍须标记待确认，不能因为是用户指定就伪造完整字段。
10. popup 显示“未授权/授权中/注入中/识别中/已识别/需要确认/不支持或失败”，失败必须给出可理解的诊断，不再无提示结束。
11. SPA 路由变化、同 URL 抽屉换岗、延迟 DOM 和旧 DOM 都要重新判定，防止把上一岗位字段贴到下一岗位。
12. 撤权、解绑或明确暂停后停止新增采集；不得因重新注入而上传旧账号队列。

3. 确定性的通用识别器；
4. 可选的大模型辅助候选，仅在工作包 E 的条件下启用。

具体要求：

1. 从现有 `tracker.js` 中拆出可独立测试的页面分类、字段候选、字段校验和归一化逻辑，避免继续把所有功能堆进一个 IIFE。
2. 保留并复用现有 JSON-LD `JobPosting`、显式钩子、可见性过滤、URL 规范化、字段来源和证据等级能力。
3. 内置适配器至少要有独立的：
   - 主机与官方跳转域名；
   - 列表/详情/状态等页面类型规则；
   - 列表卡片、详情链接、标题、公司、地点、JD、批次等提取规则；
   - DOM 就绪条件与 SPA 失效处理；
   - 对应 fixture、预期字段和适配版本。
4. 不得只根据域名或 URL 就返回“识别成功”。URL 命中后仍须验证 DOM；URL 未命中但用户明确指定招聘页时，允许走通用识别。
5. 通用识别优先使用确定性的结构和语义证据：JSON-LD、标题与“岗位职责/职位描述/任职要求/工作地点”等标签的邻近关系、可见卡片结构、详情链接和字段一致性。
6. 多岗位 JSON-LD、列表页和详情页不得混成一个岗位；无法唯一归属时返回列表预览或待确认，不正式入账。
7. 对 Shadow DOM、iframe、动态抽屉和异步渲染：能安全支持则实现并测试；不能支持则明确诊断，不空报成功。iframe 仍需对应 frame 来源已授权。
8. 公司、岗位、链接等核心字段缺失时保留 `null` 和待确认原因，禁止填“某公司”“某岗位”等假数据。

## 八、工作包 D：实现可验证的站点布局学习与记忆

本任务优先实现确定性的“站点档案学习”，不是训练模型，也不是让插件无监督自我修改代码。

1. 新增独立存储，例如 `tounar.siteProfiles.v1`，不要塞进现有配对设置或事件队列。
2. 每个档案至少包含：
   - `profile_key`
   - `origin`
   - `path_pattern`
   - `page_type`
   - `schema_version`
   - `profile_version`
   - `selectors` / 结构化提取规则
   - `source`（user_confirmed、rule_learned、llm_candidate 等）
   - `enabled` / `layout_state`
   - `validation_count`
   - `last_validated_at`
   - `last_seen_at`
   - `last_success_at`
   - `last_failure_at`
   - `consecutive_failures`
   - `last_error`
   - `created_at` / `updated_at`
3. 只保存选择器、路由模板、页面类型和运行状态；不保存岗位正文、完整 JD、页面快照、表单值、联系方式或敏感 URL 参数。
4. 选择器生成优先使用稳定属性、语义标签、`data-*`、`itemprop`、ARIA 和可验证的字段锚点；避免脆弱的全路径 `nth-child` 和随机哈希 class。
5. 每个候选选择器必须在当前页面用安全的 `querySelector` 验证，并检查可见性、字段唯一性、文本合理性和详情链接归属；非法选择器要隔离而不是使整个内容脚本崩溃。
6. 档案晋升满足任一条件：
   - 用户在预览中明确确认；或
   - 至少两个同布局的不同岗位页得到一致的高把握结果，并通过字段校验。
7. 单次低把握识别、单次模型输出、字段冲突结果不得自动晋升。
8. 已验证内置适配器优先于学习档案；学习档案不得覆盖腾讯等已验证规则。
9. 网站改版或连续失败时，将档案标记为失效/待复核，记录更新状态和诊断，回退通用识别；不得继续用旧规则制造错误岗位。
10. 档案按源和页面类型隔离；设置容量、版本兼容和清理策略，并提供“忘记此站点布局/重新学习”。
11. 浏览器重启后档案可恢复；撤销全部授权及删除本地数据时能够同步清理。
12. 本地探测可返回 `profile_key/profile_version` 供诊断；不要为了上传学习档案而擅自扩展 C1 或新增服务端业务表。

## 十一、速度与稳定性验收口径

“与腾讯招聘官网一致”必须变成可测指标，不得凭体感声称。

1. 先在相同浏览器、相同页面类型、相同网络/缓存条件下测出当前腾讯基线；冷启动和热启动分开。
2. 至少分别记录：
   - 授权完成到开始探测的延迟；
   - DOM 就绪到首个可用页面类型/字段预览的耗时；
   - DOM 就绪到详情字段完成的耗时；
   - 成功率、字段缺失率和失败原因。
3. 用户关闭权限弹窗后，对已加载页面应在 1 秒内开始识别；这是“开始识别”指标，不把页面自身加载时间算成插件解析时间。
4. 首批可正常访问且完成适配的网站，热路径“首个可用预览”的 P75 目标为不超过腾讯同条件基线的 1.2 倍，同时报告 P50/P75/P95 和样本量。
5. 如果无法复现腾讯基线，明确列为未验证并给原始测量，不得编造毫秒数。
6. 现有“岗位可见累计 ≥3 秒才生成 job_viewed”是业务规则，不是抓取缓慢；不得通过取消 3 秒规则伪造速度提升。
7. 不得简单删除必要的 DOM 防抖或旧节点校验来提速；优先采用就绪条件、MutationObserver、缓存和按需重提取，避免无意义的全 DOM 高频扫描。
8. 失败样本必须计入成功率；不能用“失败得更快”冒充性能达标。

## 十二、必须补充的测试

1. 已打开页面授权后，不刷新即可注入、探测和展示。
2. 重复授权、重复注入、SPA 重入不产生重复监听器和重复事件。
3. 用户取消权限、非 HTTP 页、第二个站点授权、撤权停采、浏览器重启恢复。
4. 真实生产授权路径测试；现有静态注入测试不能替代。
5. 每个已验证站点的列表/详情 fixture 字段回归和 URL 正负例。
6. 延迟 DOM、持续 Mutation、SPA 换岗旧 DOM、同 URL 抽屉换岗。
7. 列表、多岗位 JSON-LD、非招聘页、登录/受阻页不误入正式台账。
8. 列表预览不生成批量 `job_viewed` 或申请。
9. 学习档案的用户确认晋升、跨页一致晋升、低把握不晋升、失效回退、跨源隔离、重启恢复和删除。
10. 非法 CSS 选择器、哈希 class 改版、字段冲突和容量清理不会使 tracker 崩溃。
11. 档案中不出现岗位正文、完整 JD、表单值、Cookie、联系方式和敏感 URL 参数。
12. 解绑、换号、撤权后旧队列不传给新账号。
13. 如果启用模型：未授权不外发、无配置可运行、失败回退、非法 Schema 拒绝、单次结果不自动学习。
14. 不得通过修改预期、删除失败用例或只跑 mock 来让测试变绿。

## 十四、最终交付格式

完成后输出：

1. **实现摘要**：实际改了什么，按授权、识别、提取、预览、学习、模型分类。
2. **变更文件**：精确路径和关键函数，不只写模块名。
3. **网站支持矩阵**：每个站点列出测试 URL、页面类型、提取方式、fixture 结果、真实浏览器结果、核心字段结果、耗时和限制。
4. **性能报告**：腾讯基线、各站 P50/P75/P95、样本量、冷热启动和成功率。
5. **测试证据**：实际执行的命令、通过/失败/未运行，不得以历史文档代替本次结果。
6. **手工验收步骤**：尤其是生产授权、登录态、SPA、跨官方 ATS 源和受限平台。
7. **未完成项**：哪些网站因登录、验证码、平台限制或缺少真实样本未验证；下一步需要什么。

最终接受标准不是“代码能编译”，而是：当前页授权后立即可见反馈、首批网站有真实证据、未知网站有安全回退、学习结果可验证可失效、现有腾讯与入账链不回归、所有能力声明都有测试或明确限制。
