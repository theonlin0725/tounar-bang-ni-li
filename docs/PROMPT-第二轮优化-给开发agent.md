## 1. 插件：做成真正"通用"的岗位抓取

### 用户原话
> 它没有一个通用的数据爬取功能。只能正确爬取字节跳动招聘官网的岗位信息；到其他岗位查看，爬取的岗位信息详情都是不正确的。

### 我读代码后的定位（请先复现确认）
- 只有字节 (`bytedance`) 适配器是 `site_verified: true`，其余 7 家白名单 + BOSS/牛客/实习僧都是草案选择器（`h1`、`.title`、`[class*="detail"]`、`[class*="description"]` 这类），在真实页面上很容易抓到导航栏、站点 logo、侧边推荐岗位、整块页面文字。
- `tracker.js` 的 `detectJob()` 是"**第一个能命中的规则就直接返回**"，没有对多个候选打分比较；命中后 `pageState.job` 就锁死，不会再刷新。
- 招聘官网大多是 SPA：路由切换后 DOM 还是上一个岗位/还在加载骨架屏，此时检测会抓到**旧岗位或占位文字**。
- 兜底链里 `og:site_name` / `document.title` / `longestTextBlock()`（取整页最长一段文字）/ `hostAsCompany()`（把域名首段当公司名）都会产出"看起来有值、其实是错的"数据，而且错值会直接写进台账（`fillMissingFields` 只补空字段，后来就算抓对了也不会覆盖）。

### 要做什么
**1.1 先摸底，再动手（必须先交这一步的结果）**
- 用 `npm run probe:site` + `npm run plugin:tryrun` 跑以下站点的真实岗位详情页（每家至少 2 个岗位，校招/社招各一更好）：腾讯、字节、阿里、美团、京东、小米、百度、网易、BOSS直聘、牛客、实习僧，外加 2 个白名单外的公司官网（任选，如 米哈游、拼多多）。
- 输出一张「字段准确率表」：站点 × {公司、岗位名、城市、批次、JD 摘要、岗位 ID、链接} → 对 / 错（错成了什么）/ 空。这张表就是本阶段的基线和验收标准。
- 把每个页面渲染后的 HTML 快照存到 `tests/fixtures/sites/<站点>/<岗位>.html`（目前 `tests/fixtures/` 是空的），后面做离线回归测试用。快照里去掉个人信息。

**1.2 把"第一个命中就返回"改成"多候选打分取最优"**
- 每个字段从多个来源收集候选：`data-tounar-*` 钩子 > JSON-LD `JobPosting` > 站点适配器选择器 > 通用启发式 > meta/og > `document.title`。
- 通用启发式要按"岗位页长什么样"来写，而不是按 class 名碰运气：
  - **岗位名**：离"投递/申请"按钮最近的标题元素（h1–h3 或字号最大的文本）；长度 2–60 字；排除 `header/nav/footer/aside` 内部、排除含站点名/"招聘"/"首页"的文本、排除列表里重复出现多次的文本（侧栏推荐岗位）。
  - **JD**：找带"职位描述 / 岗位职责 / 工作职责 / 任职要求 / 职位要求 / Job Description / Responsibilities / Requirements"小标题的区块，取其后正文；**不再用 `longestTextBlock()` 当兜底**。
  - **城市 / 批次 / 岗位 ID**：按"标签: 值"就近取（工作地点、城市、Location、招聘类型、职位 ID 等），批次用现有 `batchFromText`。
  - **公司**：适配器固定值 > JSON-LD `hiringOrganization` > `HOST_COMPANY` 映射 > 页面"公司名"标签就近取；**聚合平台（BOSS/牛客/实习僧）必须从页面公司卡片取，取不到就留空**；删掉 `hostAsCompany()`（域名首段当公司名）这种兜底。
- 每个字段带一个 `confidence`（高/中/低），随事件 payload 上报（`field_confidence`）。**低把握的字段宁可留空显示"待补充"，也不要写一个错值。**

**1.3 解决 SPA 时序问题**
- 路由变化或首次进入后，用 `MutationObserver` 等页面"安静"约 800ms（且已出现岗位名候选）再检测；骨架屏/"加载中"文本不算。
- 发事件前再校验一次：当前 DOM 里的岗位名 == 检测时的岗位名，不一致就重新检测。
- 同一 URL 下内容变了（站点用弹窗/抽屉切岗位）也要能重新识别。

**1.4 补齐 8 家白名单的专属适配器**
- 用 1.1 的快照逐家写选择器 + `refine()`（参照字节的写法）。验证过的改 `site_verified: true` 并写 `verified_at` / `verified_paths`，证据补进 `docs/SITE-ADAPTER-EVIDENCE.md`。做不到的如实留 `false` 并写原因（如需登录、反爬）。

**1.5 台账侧：后到的好数据能纠正先到的错数据**
- 服务端记录每个字段的来源和把握度（可复用 `application_field_sources`，加 `confidence` 列）。
- 规则：新值把握度更高 → 覆盖旧值；用户手动改过的字段 → 永远不被机器覆盖。
- 给一个一次性修复脚本：把现有台账里明显是兜底产生的错值（公司名 = 域名首段、岗位名含"招聘/官网"、JD 是页面导航文字）标成"待补充"，先 dry-run 输出清单给用户看，用户确认后再执行。

**（可选，不阻塞本轮）** 规则把握度低时，用已接的云端大模型（`server/src/cloud/llm.js`）对"岗位名附近的有限可见文本（≤1500 字）"做字段抽取；必须有开关、只在低把握时调用、结果仍按"中把握"处理。

### 怎样算做完
- 1.1 的准确率表重跑：8 家白名单 **公司 + 岗位名 100% 正确**，城市/JD 摘要 ≥ 80% 正确或为空（**错值 = 0**）；白名单外 2 个站点岗位名正确。
- `tests/fixtures/sites/` 快照有离线回归测试，后续改选择器能自动发现退化。
- 字节原有表现不退化（E2E 原用例全绿）。

## 2. 提醒邮件：换推送形式

### 2.1 落款日期 = 我收到原始邮件的日期

**用户原话**
> 推送邮件的落款日期是我收到邮件的日期，而不是你推送的日期。你可以知道我的邮件的测评/笔试/面试/拒绝，那么推送给我的这个邮件，其落款日期应该是我收到该邮件的日期。

**定位**
- `reminders.js` 的邮件头和正文用的都是 `shanghaiDateKey(new Date())` + "08:00 批次"，也就是**推送日期**；「有进展」条目只有一句 `A → B` 的摘要，没写这条进展是哪天收到的。
- 真 bug：`createReviewForEvent()` 插入 `review_items` 时**从来不写 `source_mail_id`**，所以 `reviewDigestState()` 和待确认列表里 `JOIN mail_messages` 取 `received_at` 永远是空，"邮件收到于"实际一直退回成入库时间。

**要做什么**
- 修掉 `source_mail_id` 不写入的 bug（`mailSync.ingestMessage` → `processMailEvent` → `createReviewForEvent` 一路把 `mail_messages.id` 传下去）；为已有的 open 复核项写一次回填迁移（通过 `events.connection_id/uidvalidity/uid` 对上 `mail_messages`）。
- `notification_outbox` 增加 `source_received_at`（原始邮件收到时间；非邮件来源用事件发生时间），写入时就存好。
- 邮件里每一条进展都按"一封招聘邮件 = 一段"来排，**每段的落款日期 = 该原始邮件的收到日期**，例：
  ```
  字节跳动 · 产品经理（校招）
  面试邀请 · 一面 · 面试时间 10月25日 14:00
  —— 2026年10月20日 收到
  [打开岗位/申请状态页]  [在台账里查看]
  ```
- 整封推送如果只有一条进展：邮件顶部日期和底部落款都用这封原始邮件的收到日期；多条时：每条各自落款，顶部写"收信日期 10月18日–10月21日"，**不再用"今天 08:00 批次"做主日期**（推送时间可以留一行小字放页脚）。
- 邮件主题也带上收信日期，例：`【帮你理】字节跳动·产品经理 面试邀请（10月20日收到）`；多条时 `【帮你理】3 条进展（10月18日–21日收到）`。
- 文本版、HTML 版、网页待确认队列三处日期口径一致。

### 2.2 笔试/面试/测评后 N 天提醒我回看

**用户原话**
> 在接到笔试/面试/测评后，系统能提醒我过了几天（比如七天或十四天），让我去回看该岗位。邮件中应附上链接，方便我直接在邮件里进行回看。

**定位**
- 现有 B 类"等待回看"只按"已投 N 天（默认 14）"触发，锚点是 `max(投递, 最近进展, 最近确认)`，没有"收到笔试/面试邀请后第几天"这个概念；邮件里只有一个 `/r/:token` 确认链接，没有直达官网的链接。
- 邮件里的 `/?panel=reviews` 链接前端根本没处理（`ledger.js` 只认 `panel=settings`），点了只会落到台账首页。

**要做什么**
- 设置页新增「笔试/面试后提醒回看」：选项 **7 天 / 14 天 / 关闭**，默认 7 天（存 `notification_preferences` 新列，如 `stage_followup_days`）。和原来的"已投 N 天"设置分开显示。
- 触发规则：状态进入 `assessment` 或 `interview` 时记下**锚点 = 那封邀请邮件的收到日期**（非邮件来源用状态变更时间；有面试时间且面试时间更晚，则锚点取面试时间）。锚点 + N 天当天 08:00 的批次里提醒一次。
  - 期间状态又往前推进（例如笔试 → 面试、面试 → offer/拒绝），旧提醒作废，按新阶段重新计。
  - 用户点了"已确认，状态无变化"后，从确认那天起再过 N 天才会再提醒；同一条最多 7 天 1 次（沿用 D06）。
  - 终态（offer/拒绝/关闭）不再提醒。
- 邮件里新增一节「该回看了」，每条写清楚：
  ```
  美团 · 数据分析师
  笔试邀请 10月12日收到，已过 7 天，还没有新进展
  [直接打开申请状态页]  ← status_url，没有就用 job_url
  [我看过了，没变化]    ← 现有 /r/:token 确认流程
  [结果出来了，去更新]  ← 打开台账并定位到这条记录的详情
  ```
- 修复/补齐深链：`/?panel=reviews` 打开待确认；新增 `/?app=<id>` 打开台账并弹出该条详情。登录态失效时，登录后要回到原深链。

### 怎样算做完
- 用测试账号造数据：收到面试邮件（收信日 = D）→ 在 D+7 的 08:00 批次邮件里出现该条，落款是 D 而不是推送日；点三个链接各自到达正确页面。
- 单测覆盖：锚点计算、阶段推进作废、确认后顺延、终态不提醒、7/14/关闭三种设置。
- 旧的"已投 N 天"提醒不受影响。

## 3. 台账：邮件联动实时改状态 + 待确认打通

### 3.1 从邮件识别到拒信/面邀后，台账实时改状态

**用户原话**
> 可以通过从邮件中获取到"拒信"或"面邀"后，对台账进行实时状态更改。合理联动插件去抓取数据，并将数据正确呈现出来。

**定位**
- `processMailEvent()` 只有在邮件里抓到 `site_application_id` 并唯一命中时才算强匹配；**"公司 + 岗位"一律进待确认**。而国内招聘邮件几乎不带申请编号，所以现在拒信/面邀基本都不会自动改台账，全堆在待确认里（用户账号里已经有十几条）。
- 公司名比对只是 `normalizeCompanyKey` 精确相等，"字节跳动 / ByteDance / 抖音"、"腾讯 / Tencent / 腾讯音乐"这类对不上；岗位名要求完全相等。
- 邮件同步每 25 分钟一次，台账页面不会自动刷新，用户感觉不到"实时"。

**要做什么**
- **匹配升级**（`findCandidates` 加一档"邮件匹配"，不要影响插件去重逻辑）：
  - 公司：别名表（中文名/英文名/主要子品牌）+ 发件域名 → 公司映射（`@bytedance.com` → 字节跳动 等，复用/扩展 `HOST_COMPANY`）。
  - 岗位：规范化后包含/相似度匹配（去掉"2027届""校招""-北京"等修饰）。
  - 给每个候选算一个**匹配把握度**：申请编号命中 = 1.0；公司命中 + 岗位高度相似 = 0.9；该公司在台账里只有 1 条进行中的申请 = 0.85；只命中公司且有多条 = 0.5。
- **自动更新规则**（总把握度 = 分类置信度 × 匹配把握度）：
  - 面邀/笔试/测评（非终态）：总把握度 ≥ 0.8 且只有 1 个候选 → 直接改台账状态。
  - 拒信/offer（终态）：总把握度 ≥ 0.9（沿用 `AUTO_TERMINAL_CONFIDENCE`）且只有 1 个候选 → 直接改。
  - 其余 → 进待确认，并把"系统猜的是哪条、把握度多少"带进去，方便用户一键确认（见 3.2）。
  - 两个阈值都放进 config，可用环境变量调。
  - 状态回退、终态被覆盖等现有保护（`applyStatusTransition`）保持不变。
- **自动改了也要可撤销**：台账详情的历史里标明"由 X月X日收到的邮件《主题片段》自动更新"，并提供"这条改错了，撤回"按钮（走现有 D05 纠错留痕，原因自动填"邮件自动判定有误"）。
- **"台账里还没这条"的面邀/拒信**（比如投递时没装插件）：进待确认，卡片上直接提供"按邮件新建一条"，公司/岗位/状态预填。
- **投递时间缺失的处理（需要用户拍板，先按默认做，放在开关后面）**：插件"看过没投"的记录收到面邀/拒信时，现在因为 D12（不许用收信时间代替投递时间）会卡在待确认。**默认方案**：允许标记为"已投"，`applied_at` 记为该邮件收到时间并设 `applied_at_precision = 'inferred_before'`，台账显示"≤ 10月20日（据邮件推断）"；开关 `D12_ALLOW_MAIL_INFERRED_APPLIED_AT`，默认开。
- **"实时"体验**：
  - 台账页每 60 秒、以及页面重新获得焦点时，用现有 `data_revision` 检查是否有变化，有变化就静默刷新，并对刚变化的行高亮 + 顶部提示"刚刚根据邮件更新了 2 条记录"。
  - 设置页（或台账顶部）提供"立即同步邮箱"按钮（已有就复用），同步完立即刷新台账。
- **插件数据在台账里正确呈现**：
  - 把第 1 部分的字段把握度带到台账：低把握/缺失的字段显示灰色"待补充"，鼠标悬停说明"插件没把握，点开可补"；不再显示错值。
  - 插件在官网"投递记录页"观察到的状态（`site_status_observed`）要走同一套匹配 + 自动更新规则，不要和邮件来源各走一套。

### 3.2 "待确认"在前端打通——用户能真正点确认并提交

**用户原话**
> 目前在前端页面中，"待确认"的逻辑尚未完全打通。点击状态后，我无法提交确认。实际上，用户无法完全确认"待确认"这一步。之前设定的是根据"智信"系数进行系统自动判断：若系数小于某值，则转人工判断。现在需要在前端进行交互逻辑的确认。

**定位（请务必先用真实账号复现，录下点击路径和接口报错）**
- 邮件进来的复核项大多数 **没有候选记录**（原因见 3.1），而 `reviews.js` 里「确认」「关联所选记录」「切换状态」三个按钮在 `candidates.length === 0` 时都是 `disabled`——用户只能"新建"或"忽略"，确认不了。
- 「直接切换状态」切到 已投/笔试/面试/offer/拒绝 时**强制要求手填投递时间**，即使候选记录本来就有投递时间，用户不知道填什么 → 卡住。
- `mail_progress`、`MAIL_MATCH_UNCONFIRMED`、`TERMINAL_LOW_CONFIDENCE` 没有中文标签，卡片上显示的是英文代码；置信度只是一串小数，用户看不懂为什么要他确认。
- 服务端多个候选时 `resolveReview` 会报"请明确选择"，前端没有引导。

**要做成的交互（每张待确认卡片）**
1. **一句话结论放最上面**，用大白话：
   > 系统判断：10月20日收到的这封邮件，是 **字节跳动 · 产品经理** 的 **面试邀请**。
   > 系统把握度 72%（低于 90% 不会自动改台账，所以请你确认一下）
2. **证据折叠区**：邮件主题、发件域名、正文片段、收到日期。
3. **三个主按钮**（任何情况下都可以点，不再因为"没有候选"被禁用）：
   - **「对，更新台账」**：把系统猜的那条记录改成系统猜的状态。系统没猜出记录时，这个按钮变成「选一条记录并更新」。
   - **「不对，我来改」**：展开 → ① 选台账记录（默认列出候选；没有候选时给一个**搜索本人台账**的下拉框，按公司/岗位搜；也可选"新建一条"并预填）② 选状态 ③ 时间字段只在**真的缺**的时候才出现，并且默认预填（投递时间缺 → 预填邮件收到日期并标注"据邮件推断"，见 3.1 开关）。
   - **「这不是招聘进展，忽略」**：二次确认后忽略。
4. **提交后**：卡片收起，toast 提示"已更新：字节跳动·产品经理 → 面试中"，台账 tab 上的待确认计数 -1，对应台账行同步变化；提供 10 秒内"撤销"。
5. **报错处理**：409 版本冲突 → 自动重新拉取并提示"这条刚被更新过，已刷新，请再确认一次"；所有错误都用中文说人话，不出现 D05/D12 这种内部编号。
6. **批量**：顶部"把握度 ≥ 80% 的全部按系统判断确认"一键批量（逐条调用接口，失败的留在列表里并标红）。
7. 待确认 tab 的计数、邮件里的"待你确认"数量、页面列表数量三者一致。

**服务端配套**
- `resolveReview` 支持"关联任意一条本人记录"（不限于 `candidates_json` 里的），仍做 owner 校验 + 版本校验。
- 新增本人台账搜索接口（或复用列表接口的 `q` 参数）供下拉框使用。
- 复核项返回时附带：系统建议的目标记录 id、匹配把握度、分类置信度、总把握度、原始邮件收到时间。

### 怎样算做完
- 用用户账号现有的那十几条待确认逐条走一遍：每一条都能通过「对，更新台账」或「不对，我来改」**成功提交**，台账状态随之变化，历史里有留痕。
- 造数据验证：高把握面邀 → 台账自动变"面试中"，无需进入待确认；低把握拒信 → 进入待确认 → 一键确认后变"已拒绝"；自动改错 → 详情里可撤回。
- `npm run test:web` 新增用例覆盖：无候选时确认、搜索关联、批量确认、409 重试、撤销。
