## 必须退回的问题

### 1. [P1] A 岗回执会在 B 岗页面提示“当前岗位已入账”

源码：[service-worker.js:37](../extension/background/service-worker.js#L37)。

`samePage()` 仅比较 `origin + pathname`，忽略 query、hash 和具体岗位身份；内容脚本收到反馈后也没有再次核对当前岗位。

真实扩展复现步骤：

1. 打开 `/jobdesc.html?postId=5001`，自然浏览产生采集事件。
2. 测试代理暂扣后端对 5001 的真实入账回执。
3. 点击页面按钮，切换到 `/jobdesc.html?postId=5002`，DOM 标题也变为“提示验收岗位5002”。
4. 释放 5001 的回执，页面读到“当前岗位已计入「看过没投」”。此时回执对应记录的岗位仍是 5001。

hash 路由的契约检查也失败：`#/job/1` 与 `#/job/2` 被判断为同页。同 URL 抽屉缺少岗位身份校验属于同类风险，本次未另做抽屉 Toast 实测。

原自动化中的 A→B 用例核对的是采集数据与台账记录，没有断言延迟回执下 Toast 仍属于当前岗位，不能作为“不串提示”的证据。

### 2. [P2] 关闭提示开关后仍可能弹 Toast，重新打开 popup 又显示为开启

源码：[service-worker.js:322](../extension/background/service-worker.js#L322)、[popup.js:308](../extension/popup/popup.js#L308)、[tracker.js:1001](../extension/content/tracker.js#L1001)。

复现了两个独立表现：

- 保存的 `pageFeedback=false` 没变，但关闭再打开 popup，复选框又显示勾选。原因是 `get_status` 没有返回 pageFeedback，前端把 undefined 当作开启。
- 开关确实为 false 时，主动断网采集仍显示“当前岗位待同步，连接恢复后自动重试”。原因是开关只拦住 SW 推送，内容脚本 `captureNow()` 的直接提示没有检查开关。

原测试只覆盖关闭开关后的在线成功路径，未覆盖主动离线提示和 popup 重开。

### 3. [P2] 自然浏览遇到断网时，用户仍然没有页面反馈

源码：[service-worker.js:105](../extension/background/service-worker.js#L105)、[tracker.js:964](../extension/content/tracker.js#L964)。

复现：提示开关开启，关闭 popup，打开一个有效岗位并自然停留至采集；测试代理断开上传连接。队列里已有 1 条待同步事件，但页面 Toast 为空。

上传异常分支只写插件状态及 badge，不把失败/待同步结果送回页面；内容脚本直接显示待同步的逻辑只在主动采集路径。这没有解决用户最初提出的“正常浏览采集时没有反馈”的完整场景。

### 4. [P2] 汇总按事件数计算，把同一岗位显示成多个岗位

源码：[service-worker.js:59](../extension/background/service-worker.js#L59)。

复现：同一个岗位在断网时主动采集两次，恢复后实际产生 2 个事件回执，但两者的 `application_id` 相同。Toast 显示：**“本页 2 个岗位已保存”**，实际只有 1 个岗位。

当前代码统计的是 bucket 中事件数量，没有按业务记录/岗位身份去重；失败项也被统一归为“待同步”，没有区分不可重试拒绝。后者是静态检查发现，本次未另做真实拒绝汇总场景。

### 5. [P1，契约检查] “已保存”兜底没有核对实际入账

源码：[service-worker.js:27](../extension/background/service-worker.js#L27)。

对源码函数输入 `accepted=true, processing_state=ignored, application_id=null`，返回 `saved`。该分支最终对应“当前岗位已保存到台账”。

这是成功判定防线的缺口，与任务书“至少核对 application_id 和最终处理结果”不一致。**本次仅复现函数契约错误，没有声称真实后端已经产生过该组合并向用户报假成功。** 它应补上明确判断后再验收。
