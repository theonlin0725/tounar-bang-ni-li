## 二、必须修复的六组问题

### 1. P1：防止 A 岗回执在 B 岗页面报成功

已复现：打开 `/jobdesc.html?postId=5001`，暂扣真实上传回执，页面切换至 `?postId=5002` 并更新 DOM 后释放回执，B 岗页面仍显示“当前岗位已计入台账”，实际保存的是 A 岗。

根因入口：`extension/background/service-worker.js` 的 `samePage()` 只比较域名和 pathname；内容脚本未再次核对反馈对应的岗位。

修复要求：

- 将采集事件绑定到来源标签页、frame/document、页面或路由版本、岗位身份。保留影响岗位身份的 query/hash，不能只比较 pathname，也不能仅靠标题区分。
- 同 URL 的详情抽屉从岗位 A 切到 B，也要识别为不同岗位。仅增加完整 URL 比较仍不够。
- SW 投递前和内容脚本显示前均验证关联有效；首次加载、页面刷新、路由切换、异步 DOM 更新都应有明确处理。
- A→B→A、旧任务重试、多标签相同链接不能让旧反馈覆盖当前任务结果。
- 已离开原岗位、关闭标签或无法证明仍属于当前任务时，在 popup 中保留可追溯结果，页面不冒称“当前岗位已保存”。列表汇总须使用列表上下文，不能套用某一个详情岗位身份。

### 2. P2：提示开关覆盖所有路径，并正确恢复显示状态

已复现两个问题：保存 `pageFeedback=false` 后重新打开 popup，复选框仍显示勾选；关闭开关后主动断网采集仍弹“待同步”。

根因入口：SW 的 `get_status` 漏返回 `pageFeedback`；内容脚本 `captureNow()` 直接显示反馈时绕过开关。

修复要求：

- 配置读取、返回、默认值与 popup 显示统一；只有尚未设置时默认开启，不能把已保存的 false 当作缺省。
- 自动采集、手动采集、处理中、成功、待确认、待同步、失败、列表汇总，全部通过统一的开关检查。
- 关闭开关时撤掉当前提示和未触发的计时器；正在处理的任务稍后返回，也不能绕过关闭状态。
- 页面已打开时切换设置应立即生效；重新打开 popup、页面刷新及 SW 恢复后保持一致。
- 关闭提示不影响采集、上传、队列、popup 状态和错误记录。

### 3. P2：自然浏览断网或失败时也要有轻量反馈

已复现：提示开启、popup 关闭，用户自然浏览岗位，事件已进本地队列但上传断开，页面没有任何提示。当前待同步提示只覆盖主动采集路径。

根因入口：SW 的 `runFlush()` 上传异常分支只更新插件状态和 badge，没有向原页面发送反馈。

修复要求：

- 自动浏览与手动采集共用状态通知逻辑。有效岗位采集已经开始后，用户能知道它正在处理、尚待同步、需要确认或失败。
- 网络中断、可重试超时等显示“当前岗位待同步，连接恢复后自动重试”；认证失败、撤销授权、不可重试拒绝应显示需要处理的具体状态，不能都说会自动重试。
- 处理中提示延迟显示，快速成功避免闪烁；超时后有明确状态，不永久转圈。
- 恢复连接后以真实回执更新结果，并继续遵守岗位身份校验和提示开关。
- 同一故障连续重试时不反复刷屏；普通非岗位页不弹采集失败。

### 4. P2：列表与批量汇总按岗位计数，不能按事件计数

已复现：同岗位断网采集两次，恢复后两个回执对应同一个 `application_id`，Toast 却显示“本页 2 个岗位已保存”。

根因入口：`deliverFeedback()` 按 bucket 中事件数量统计。

修复要求：

- 已保存记录按实际 `application_id` 去重；尚未入账的任务按可靠且有站点作用域的岗位身份去重，不能仅凭公司和标题。
- 同一岗位重复浏览、主动采集、列表与详情事件，不得重复计为多个岗位。不同岗位即使同名也不能合并计数。
- 区分已保存、待确认、待同步和不可重试失败。失败不能全部显示为待同步；旧失败不能覆盖后来已经确认的成功。
- 列表分多次 flush 上传时，提示数字要有清晰口径。若显示“本页 N 个”，就应维护本页本轮的正确汇总；若仅指本批，使用准确文案，不能把局部批次数冒充整页总数。
- 自动浏览无实质字段变化时保持静默；仅更新浏览时间不能冒充“岗位信息已更新”。主动重复采集可以反馈“该岗位已在台账中”。
- 汇总与 popup、实际台账数量一致；同页维持一条提示，避免批次结果轮番刷屏。

### 5. P1：成功提示必须验证真正入账

契约检查已失败：`feedbackStatus()` 接到 `accepted=true, processing_state=ignored, application_id=null` 时仍返回 `saved`。

这项目前是源码函数层面的复现，不是声称真实后端已经产生该组合。修复时应保留这个证据边界，同时补上防线。

修复要求：

- 将 Toast 与 popup 使用的回执解释统一，避免两个地方对同一回执给出不同结果。
- 只有明确的业务记录 ID 与成功处理状态共同成立，才显示“已保存/已计入台账”；`outcome` 再用于区分新增、更新和无变化。
- 仅入队、HTTP 200、`accepted=true`、ignored、cancelled、缺少记录 ID、未知回执或处理失败，均不能走成功兜底。
- 复核项显示“需要确认”，业务保存与岗位投递阶段分开判断。事件 `processing_state=applied` 不是“用户已投递”。
- 新旧回执兼容时采取准确的降级文案；无法确定状态就说明尚未确认保存，不猜成功。
- 补齐字段变化与纯浏览时间变化的 outcome 判断，确保 updated/unchanged 的含义真实。

### 6. P1：SW 休眠恢复后保留有效反馈关联

已知实现：`pendingTabs` 仅存在 SW 内存。对方报告已承认休眠后丢失关联、Toast 不显示；这不满足原任务要求。

修复要求：

- 为排队事件保存最小必要的来源和任务元数据，采用能跨 SW 生命周期恢复的机制，或提供等效的可验证恢复设计。
- 恢复后在任务仍属于有效页面/岗位时，正确显示待同步或最终结果；不能仅因 SW 重启就静默丢失反馈。
- 对已经关闭、导航或失效的页面保留 popup 结果，不把恢复后的回执发送给碰巧复用 tab ID 的其他页面。
- 设置过期、去重和清理规则；队列清空、权限撤销、设备解绑后旧通知不能再次出现。
- 用实际停止并重启 SW 的测试验证；保持 worker 常驻、只重开 popup 或只证明队列还在，均不算通过。

## 三、修复后的统一行为

| 条件 | 页面应有的行为 |
|---|---|
| 新建未投递记录且服务端已确认 | 已计入看过没投；确有缺字段再附待补充说明 |
| 可靠字段补全成功 | 岗位信息已更新 |
| 自动重复浏览、没有实质变化 | 静默 |
| 主动采集已存在的岗位 | 该岗位已在台账中 |
| 投递/阶段事实可靠更新 | 投递进展已更新到台账 |
| 需要用户确认 | 需要确认，链接到相应入口 |
| 仅入队、网络不可用 | 待同步，不能报已保存 |
| 不可重试失败/需重新授权 | 清楚说明尚未保存及查看原因的入口 |
| 已离开原岗位或当前页面身份不明 | 不冒充当前岗位成功，结果保留在 popup |
| 提示已关闭 | 所有页面提示均不出现，采集和 popup 照常工作 |

保留轻量样式、手动关闭、约 4 秒成功提示、合理的需操作提示时长、`aria-live=polite`、不抢焦点及窄窗口兼容。链接使用当前后台配置，按 URL 规则保留必要分享参数并正确加入 app/panel 参数，仅在用户点击时打开。

## 四、必须新增并实际执行的验收

每条都要断言实际 Toast 文本/是否存在、对应事件和业务记录，不能只验提取器或台账数据。

1. query 换岗、hash 换岗、同 URL 抽屉换岗：延迟 A 回执到 B 页面后，不能显示 A 的成功提示。
2. 同一岗位 A→B→A、两个标签并行、标签刷新/关闭：结果不串页、不被旧任务覆盖。
3. 关闭开关后，自动/手动采集的成功、离线、失败及处理中状态都不弹；popup 重开显示仍关闭，采集状态继续更新。
4. popup 关闭时，自然浏览断网有待同步提示；恢复后正确处理，连续重试不刷屏。
5. 未配对、认证失败、不可重试拒绝分别有准确结果，不能假报成功或承诺无效重试。
6. 同岗位两个事件恢复同步显示一个岗位；多个不同岗位、重复事件、混合成功/待确认/待同步/失败的汇总数量正确。
7. 自动浏览只有时间变化时静默，真正补字段时提示更新；主动无变化采集有准确反馈。
8. `accepted` 但 ignored/无 ID、cancelled、failed 和未知回执不显示保存成功；分类函数测试和真实后端链路测试分开记录。
9. 队列未清空时停止并重启 SW；同一有效岗位的结果能恢复显示，已经离开的页面不会收到错误提示。
10. 正常本机后台、带必要查询参数的后台地址下，“查看台账”能定位实际记录或复核入口。
11. 对提示开关开启的正常成功路径做回归：实际入账、正确 Toast、关闭 popup 后继续工作、自动消失、可关闭、无焦点抢夺。

原 `.tmp` 验收脚本可作为失败样本起点，将有效回归整理进正式测试目录。补强只检查“包含本页”等过弱断言，验证数字、岗位 ID 和时序。不要删除失败用例、改变正确预期、缩减分母或只截成功截图来制造全绿。

主验收使用真实扩展脚本、隔离后端和本地可控页面；可用测试代理注入断网和延迟。直接调用函数或模拟回执只能作为契约/单元测试，不能代替实际页面上的反馈验证。记录预授权、登录态等测试条件，未测场景继续标未验证。
