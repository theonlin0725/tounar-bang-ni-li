## 建议开发顺序

1. **先让收信可用、可观察。** 把收件调度与提醒发信独立配置；设置页展示读取范围、上次成功、本轮新增／处理／待确认／错误数和剩余积压。支持本人显式切换到“招聘候选正文”，说明模型处理和摘录留存范围。修复单段纯文本／HTML 和下载失败的重试，分批续扫；落库与提交游标前校验绑定版本和租约，防止断开后被旧任务重新标为已连接。入口在 `server/src/modules/data-capture/mail/`、`server/src/jobs/scheduler.js`、`web/assets/js/views/settings.js`。
2. **统一邮件的模型判断。** 建议为邮件增加可切换的 Flash 直判模式，让自动同步和人工确认复用同一判断逻辑；保留现有 Jev 路径供对照和回退，邮件开关独立于插件。复用现有抽取器，输出“是否本人实际进展、公司、岗位、申请号、状态、原文证据”。服务端在本人未归档台账中优先查可信申请号，再查公司＋岗位＋批次；多个合理候选、字段冲突、只有公司或证据不足，一律交人工选。无候选且公司、岗位、实际进展都有证据时才自动新建。模型超时进入有上限的重试，最终失败可见、可人工处理。入口在 `modules/recruitment-intake/{llm,workflow,confirm}.js`（相对 `server/src`）与 `domain/mailMatching.js`。
3. **统一三个入口的写账规则。** 在事务中重读目标版本，校验原信时间、人工修改时间、终态和事件去重，再一起更新台账、历史、邮件、事件、复核与通知。已投递收到新测评邀请，更新同一申请 ID，保留原投递时间。旧信、重复信和迟到的投递回执不能冲掉后续进展。同一公司多岗需选定目标；模型不可凭公司名覆盖。保留已有 `source_method` 的兼容性，增加可查询的变更原因“用户手动／邮件自动／邮件人工确认”，详情展示原信时间及变更前后值。对齐 `closed` 的前后端枚举、人工确认和忽略后的邮件状态。入口在 `server/src/domain/{applications,reviews,ledger}.js` 以及网页 `reviews.js`、`detail.js`。
4. **先回放，再灰度。** 用隔离库跑规则与 Flash 对照，比较错关联、重复建账、错误回退和待确认比例；先记录模型建议，再对小范围新信开放自动写入。存量 pending 按原事件及已关闭复核做只读对账，生成修正清单；避免全量重跑模型改写已处理台账。灰度异常时关掉邮件自动写账，继续收信并保留人工确认。

**阶段口径**：本期可以直接验收“已投递 → 测评”。对后续“测评 → 面试”，旧规则要求部分情形拆条，AI 路径已有原地更新测试。建议对可唯一识别的同一次申请原地推进，以历史展示各阶段；不同申请号或不同批次保留独立记录。跨阶段策略单独验收，历史拆开的记录不自动合并。

## 最小验收

- 同一真实测试邮箱完成首扫和定时增量。邮件头模式只取头；经授权的正文模式能识别正文中的岗位。多于 50 封可续扫，失败可重试，断开后旧任务不能继续写。
- 给已有“已投递”的唯一岗位送入一封新的测评邀请，贯通 IMAP → Flash → 台账 → 网页历史，核对申请 ID 不变、状态变为测评、历史标明“邮件自动”、重放无第二次变更。
- 同公司两岗且邮件未指明岗位，保持两条台账原状。人工选定其一后仅更新该条，历史标明“邮件人工确认”，邮件与复核同步结案；忽略则不改台账。
- 用户手动改状态后重放旧信，保留人工结果；随后收到更晚且证据充分的新进展，可以继续推进。补抓旧回执、重复点击、并发确认、模型故障、终态冲突都不能制造重复或错误更新。
