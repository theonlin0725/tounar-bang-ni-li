## 一、核心目标

帮我把招聘网站浏览记录和招聘邮件整理成可追溯的求职台账：

- **正常浏览岗位、尚无可靠已投递证据 → 自动进入「看过没投」。**
- **已有可靠投递、笔试/测评、面试证据 → 自动进入「投递明细」，准确显示对应阶段。**
- **真正存在申请归属歧义或证据冲突 → 进入「待确认」，并能查看足够判断的页面或邮件证据。**
- 可以外接大模型辅助提取、匹配和分类，但结果必须经过校验，不能靠猜测制造投递事实。

优先修复用户已遇到的两个问题：浏览记录错误堆积在「待确认」；展开「查看邮件 / 页面证据」后看不到可用内容。

## 三、先分清三个不同维度

不能把以下三个维度混成一个状态：

| 维度 | 含义 | 展示与处理 |
|---|---|---|
| 求职阶段 | 尚无投递证据、已投递、笔试/测评、面试、录用、拒绝等 | 决定台账入口与阶段 |
| 字段完整度 | 公司、岗位、城市、JD 等是否齐全 | 用「待补充」标记；缺字段不等于已投递或待确认 |
| 处理结果 | 已识别、待上传、上传失败、已保存、需确认 | 插件回执和异常诊断 |

当前 `processing_state=applied` 表示事件已应用，不能据此显示“已投递”。普通浏览记录的业务状态仍应是 `pending / has_applied=false`。

「看过没投」表示系统尚未取得已投递证据；若后来收到证据，应更新记录。不能因为页面没有“已投递”文字，就覆盖系统已知的投递事实。

## 四、插件：识别岗位并正确入账

### 4.1 正常浏览流程

在用户授权的招聘网站，识别当前可见的岗位列表、详情页或详情侧栏，提取页面实际存在的：

公司、岗位名、岗位 ID、岗位链接、城市、完整 JD、招聘批次，以及有明确原文的投递/申请状态。保留来源、采集时间和必要原文证据。

- 首次授权后能处理当前页；后续正常浏览无需每次打开插件或手动采集。
- 详情可沿用真实可见停留 3 秒的规则；列表发现不能伪造“打开过详情”或停留时间。
- 列表没有全文时标记「JD 待补充」；打开详情后补全原记录，保留段落，不用列表摘要覆盖全文。
- 同岗位重复浏览只补全；不同稳定 ID 的同名岗位不能误合并；SPA 切换不能串用前一个岗位的字段或异步结果。
- 用户改过的字段不能被自动抓取覆盖。

### 4.2 浏览缺字段的正确处理

已经能够判断为真实岗位、且保留可追溯岗位链接或稳定身份的浏览线索，应在「看过没投」可见。公司、城市、批次或 JD 缺失时，保留已知信息并标记待补充，后台可以继续补全；不得仅因字段不全就让普通浏览记录消失到「待确认」。

公司或岗位名称确实无法提取时，不猜值，不把“待补充公司”等占位文案存成真实实体。检查现有数据库非空约束、API 校验和前端展示，设计兼容的不完整岗位表示，必要时增量迁移。

真正连岗位身份都无法确定的原始片段，保留采集诊断与原始来源，说明缺失原因，允许重新识别；不能把首页、登录页、验证页、广告或加载壳当岗位批量入账，也不能把每次失败都生成一条同样的待确认。

确有多个申请候选时，不强行合并。保留可追溯的浏览线索，并单独提出具体的关联问题；归属问题不能伪装成投递事实。

### 4.3 投递判断

允许确立投递事实的证据包括明确的提交成功回执、可关联到该岗位的官网申请状态、用户本人收到的可靠投递确认邮件，以及用户明确手动确认。

点击“投递”、打开申请表、开始填写、跳转登录、与招聘者聊天，均不等于提交成功。失败或取消提交不得进入已投递统计。

浏览记录后来被确认已投递时，在同一申请身份下更新并保留浏览历史，从「看过没投」移入「投递明细」，避免再造一条重复申请。没有准确投递时间时应展示未知或有来源的推断时间，不能把采集时间、邮件收到时间冒充实际投递时间。

## 五、邮件与前端：阶段正确、历史可见

### 5.1 两类来源进入统一处理流程

网页事件与招聘邮件应使用一致的身份匹配、状态处理、历史记录和前端投影。邮件解析需覆盖：投递确认、笔试/测评邀请及结果、面试邀请及安排、明确完成或结果通知，以及原有录用/拒绝处理。

- 规则足够明确的事件直接归类；不能默认所有邮件都必须人工处理。
- 优先使用申请号、岗位 ID、可信链接和可核对的字段；有多条同公司同岗位申请时不得仅凭公司名合并。
- 没有浏览记录但邮件已能可靠确定岗位和阶段时，应能自动建立对应记录，标注邮件来源。
- 不能只因为已有记录处于另一个阶段，就把所有新阶段邮件卡在待确认。
- 同一封邮件重复同步不产生重复记录或轮次；旧邮件晚到不得覆盖新的状态。无法确定发生顺序的冲突保留证据再确认。
- 一般招聘宣传、推荐岗位或通用活动邀请，不得被误判为用户已经投递该岗位。

### 5.2 前端入口与展示

沿用现有主入口：**投递明细 / 看过没投 / 待确认 / 已归档**。

「投递明细」内应容易找到已投递、笔试/测评、面试记录；可提供阶段子 Tab 或清晰的快捷筛选。标签、数量、列表筛选和详情必须使用相同口径，不能出现后台状态正确但界面查不到。

每条记录至少显示公司、岗位、当前阶段、阶段时间、信息来源、关键证据入口。详情展示完整 JD、状态历史和人工修改入口；新记录或阶段变化自动出现，无需手动刷新。

必须区分：

| 原文证据 | 合理展示 | 不能直接断言 |
|---|---|---|
| 投递成功/申请已收到 | 已投递 | 已通过筛选 |
| 笔试或测评邀请 | 笔试/测评阶段 · 待参加 | 已完成笔试 |
| 明确的笔试完成或结果 | 笔试/测评阶段 · 已完成/结果 | 已进入面试，除非有证据 |
| 面试邀请/时间安排 | 面试阶段 · 待参加/已预约 | 已完成面试 |
| 明确的面试完成或结果 | 面试阶段 · 已完成/结果 | 已获得 offer |

已有 `docs/MAIL-STAGE-RULES.md` 约定笔试与面试分别保留，以及按后续邮件推进轮次。本轮应保留用户查看各阶段历史的能力，不得悄悄合并或删除历史阶段记录；同一申请的阶段记录也不能重复计入投递总数。轮次、重复通知和改期应有专门样本验证；如果调整旧规则，必须明确写出新行为和兼容方案。

## 六、待确认：必须能看到判断依据

「待确认」只承接真正需要用户决策的问题，例如多个申请候选、来源矛盾、无法可靠判断的投递/阶段事实。字段待补充本身不应阻塞可识别的普通岗位进入「看过没投」。

修复证据从存储、API 到界面的完整链路，不能只修改折叠标题。

- **页面来源**：显示原岗位标题、公司（如有）、岗位链接、站点、采集时间、已保存的 JD/状态原文及缺失字段。打开原网页与查看已保存内容分开，网页失效时仍能解释当时判断依据。
- **邮件来源**：显示主题、已保存的发件信息、原信收到时间、已授权保存的正文或片段、提取出的字段和对应证据。可用原信链接则提供；没有可靠链接时不伪造。
- 按 `source_event_id` / `source_mail_id` 读取当前用户的来源，不混入别人的数据。HTML 邮件安全转为文本或经过清理后显示。
- 展开时有明确加载、失败与重试状态；历史来源已删除、仅授权读邮件头、没有保存正文等情况，要具体解释，不能留下空白面板。
- 只有主题/片段的数据不能宣称“完整原信”。需要进一步读取时沿用邮箱授权范围。
- 页面记录使用「按页面信息新建/补全」等对应动作，不能一律显示「按邮件新建一条」。
- 原始证据、系统建议和人工修改应能区分，确认/忽略/撤销后计数及台账同步变化。

已定位的检查入口：`server/src/domain/applications.js` 的 `processView` / `reviewForEvent` / `createReviewForEvent`，`server/src/domain/ledger.js` 的复核接口，以及 `web/assets/js/views/reviews.js`。现有证据区只读少数摘要字段，插件普通浏览的复核证据又未带完整页面信息，应先复现这条链路。

## 七、外接大模型的落地要求

将大模型作为可选能力接入实际流程，而不是仅增加一个未被调用的函数。

- 可配置提供方、模型和服务端凭据；沿用可用的现有提供方，或通过统一接口支持外部模型。凭据不得进入插件、前端或日志。
- 输入限定为授权的岗位文本或必要邮件内容。页面/邮件中的指令一律作为待分析数据，不能覆盖系统规则或触发外部操作。
- 输出使用结构化 schema：岗位身份线索、字段值、阶段、阶段完成状态、时间及精度、匹配候选、引用证据、缺失项。未知值必须允许为空。
- 模型结果经字段、来源、身份和状态校验后，调用与规则引擎相同的写入接口，保留使用的模型版本、证据与变更历史。
- 有可验证原文且唯一匹配的结果可自动补全/归类；模型自报高置信度不能单独作为提交成功或自动合并的依据。
- 超时、无配置、限流、异常 JSON、空结果和重复响应均有退路，不能阻断已可靠识别的浏览记录，也不能悄悄丢失邮件。

当前已有 WorkBuddy 邮件兜底分类；`llmExtractPageLead()` 没有接入页面处理链路。先复用并补齐接口，避免另造一套与现有台账脱节的数据流程。没有可用配置时，可以完成接入和隔离验证，但报告必须区分真实模型测试与模拟响应，不能宣称真实服务已验收。

## 八、处理已经错误进入待确认的历史记录

新数据修好后，用户已有数据也要能恢复。

先在当前验收库副本上输出迁移预览：可恢复到「看过没投」的普通浏览、可按稳定身份补全现有记录的事件、仍需确认的真实冲突，以及原始证据不可恢复的项。

只对来源可核对的普通浏览线索进行幂等修复，补全或建立未投递记录、关联原事件并关闭已解决的误分类复核项。重复运行不增加记录；保留原始证据、迁移理由和回滚方式。不能一键把全部待确认转为未投递，更不能转为已投递；人工确认过的阶段不能被覆盖。

## 九、验收标准

先给本次两个用户问题建立会失败的回归，再修复。完整结果必须验证到实际前端，不只检查提取函数或 HTTP 200。

| 场景 | 必须看到的结果 |

| 腾讯正常浏览多个岗位 | 自动出现在「看过没投」，没有新增无意义的待确认 |

| 可靠提交回执或投递确认邮件 | 正确申请进入「投递明细」，计数一致 |
| 已投递后再次浏览 | 不退回「看过没投」 |
| 笔试邀请、完成、面试邀请、完成 | 阶段与完成状态正确，各阶段历史能找到 |

| 重复同步、旧信晚到、面试改期 | 不重复、不错误退阶段，不把重复通知当新轮次 |

## 十、交付要求

交付实际修复、数据迁移方案与结果、可重复测试命令、前端截图/关键证据、更新后的自测教程和剩余问题。区分「代码已写」「隔离测试通过」「真实样本通过」「用户问题已复现并修复」，不要给无法核实的完成百分比。

完成标准是：**用户授权后正常浏览，岗位自动进入看过没投；发生可靠投递/笔试/面试进展后，前端自动显示在正确位置；每次分类都有证据可看；用户无需逐条代替系统整理正常数据。**
