# DeepSeek 开发任务单 · 校招官网点击岗位后的自动整理

在当前工作区基线 ae126f3（0.2.9）上实施、运行测试并交付结果。目标用户从清单中的校招入口进入，亲自点击一个岗位，正常阅读，随后在台账“看过没投”中看到该岗位经模型整理的 JD。列表导航只供验收脚本模拟用户操作，插件产品端不增加翻页或批量抓取。

## 1. 先取得可比较的基线

- 以 docs/recruitment-company-urls-20261118.csv 的公司行号为主键，对照 docs/campus-generalization-matrix-20261119.csv。旧的 chain-all.mjs 等脚本直接打开详情并调用 capture_current_tab。自动补测 auto-detail.mjs 直接打开 3 个预授权详情并查询后端，三条记录的 model 字段为 null。保留这些证据，各自标明能证明的环节。
- 建一条可复跑的纯自动验收路径。从隔离库、正常配对和真实授权流程起步，记录基线版本，打开 CSV 校招入口，通过可见导航和岗位卡片进入详情，兼容同页、弹层和新标签。在前台等待既有可见停留时间。禁止测试主动发采集消息、直接调模型或造事件入账。已知详情直链可单独用于定位故障。至少用一个跨域样本实走授权、返回岗位后继续的流程，不用改 manifest 预授权来证明这条链路。
- 对同一次访问关联可核验的岗位身份、脱敏的模型调用与成功结果来源、job_viewed、台账记录 ID 和真实前端渲染。验证页面真实标题、雇主、职责/要求与前端对应，整理内容没有混入推荐岗位。不要靠 JD 长度推断模型成功。保留规则兜底，同时区分模型关闭、超时、模型明确拒绝和来源未证实。安永、玛氏先复核是否确为单岗位，再决定应整理还是应拒绝。

## 2. 用失败样本驱动共性修复

1. 优先复现 tracker.js 中 detectAndTrackRoute、detectJob、tickDwell 对全页 lastDomChange 的依赖。用带轮播或时钟的页面、延迟加载正文的 SPA 做对照。以当前可见岗位面板及其规范化正文判断稳定性，正文准备好后在有限时间内触发，保持可见停留语义，避免对全页高频扫描。
2. 复用已有 JobPosting、可信选择器、详情面板和适配器。补上可见列表与详情并存、同 URL 换抽屉、新标签及返回切换等情况。按当前岗位容器提取标题、职责、要求和已出现的字段，剔除推荐、导航和表单。对真实样本证实的开放 Shadow DOM、可读同源 iframe 问题再做受限支持。优先按招聘模板修一次，并用另一家公司验证；单站特例需附复现。
3. 复测 A 岗模型未返回即切到 B 岗、刷新同一岗位以及打开同名不同岗位。把请求结果与发起时的岗位身份和正文版本对应起来，沿用已有幂等机制，避免旧响应入错岗、漏掉 B 或重复入账。验证暂时性失败的恢复路径及重复调用次数。明确拒绝的多岗/项目介绍页面不可凭兜底生成假岗位。
4. 从实际入口、跳转终点和共享平台租户定位授权问题。复用“数据与授权”的用户手势，在缺少最终域名权限时说明需要授权的站点，验证授权后能继续采集。保留租户、可见正文和既有隐私门槛。未授权页、列表、公告、失效岗位、登录页、简历或投递表单作为反例，断言零 JD 模型请求和零新增“看过没投”。

## 3. 扩覆盖并交付

- 逐行处理 130 家。优先跑旧自动样本和已有校招链接，再补银行/券商自建站、北森或 hotjob、跨域共享 ATS 等未充分验证的类型。每家从入口尝试一个当前可点的校招岗位。登录/验证码、无在招、无公开入口、外站超时、导航脚本失败、插件漏识别分别记录，社招样本单列。对导航失败但能打开详情的公司保留两份结果，方便区分测试工具与产品问题。
- 每次共性修复后重放原失败样本，加上同模板未用来调规则的公司，并回归旧样本与负例。目标是已确认可访问、已授权的真实校招单岗位全部自动整理到前端，反例零误采，快速切岗不串岗，同一岗位不重复建账。有缺口就列出具体公司和失败阶段。
- 交付可重复运行的验收命令、代码改动、必要回归用例、逐公司矩阵和简报。矩阵保留入口、最终详情或面板标识、授权、动作、模型来源、入账、前端核验及失败原因。以同批样本对比修前修后；单列新增覆盖。分别报“完成纯自动链路的公司数 / 130”和“完成纯自动链路的有效校招详情数 / 已访问且确认有效的校招详情数”，另列因缺授权或外部条件受阻的数量。用隔离数据复跑原有插件、模型、权限和网页回归，报告实测结果及遗留项。此次交付限本地开发与验收。
