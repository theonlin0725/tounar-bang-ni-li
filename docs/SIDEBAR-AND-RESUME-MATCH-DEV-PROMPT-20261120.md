# 开发提示词｜TOUNAR 左侧导航与简历匹配分析

请在现有“帮你理”项目完成两项可分别验收的改动。第一项让用户从左侧找到已有工作入口，继续完成原来的操作。第二项让用户针对**一个真实岗位和自己的一份简历**，看懂是否具备所需能力、是否值得优先投递、判断出自哪里，并能纠正判断。参考图用于把握导航层级、密度和选中态。页面正文、卡片和交互应服从项目现有视觉语言。

## 一、先迁移导航，再做视觉调整

桌面采用“左侧导航＋右侧工作区”。导航从上到下放品牌标识与“TOUNAR · 帮你理”、工作入口、设置与工具、当前账号及退出。以约 224px 为桌面起点，给台账表格留出宽度。沿用现有深绿、米白、细分隔线与中文系统字体；图标配文字，选中项用浅绿底、深色文字和清晰的焦点轮廓。数字徽标右对齐。长邮箱允许截断并可查看完整值。

| 侧栏位置 | 对应现有功能 | 开发要求 |
|---|---|---|
| 投递台账 | 默认投递明细、看过没投、已归档，以及现有三项统计 | 默认仍进投递明细；保留后两项作为子视图。累计投递、进行中、面试中继续在主区显示。参考图里的“看板”无需新建独立页面。 |
| 待确认 | 现有 reviews 视图 | 提升为一级入口。使用当前账号的 `counts.pending_review`，处理完及时刷新；加载失败不显示假 0。截图中的 2、28 仅示意，台账徽标如无一致口径可省略。 |
| 匹配分析 | 现有岗位对比、未投递推荐，加本次单岗位匹配 | 保留跨列表勾选和带入岗位的入口。在此可从本人台账选择一个岗位开始匹配；从岗位详情也能带入当前岗位。 |
| 简历库 | 现有简历上传、粘贴、文本修正、分析、画像和版本列表 | 可与匹配分析复用现有 career 视图及数据。旧“简历与 AI”链接仍能到达原功能。 |
| 设置与工具 | 提醒设置、数据与授权、下载插件、安装指引、邮件测试与模板 | 沿用原按钮的对话框、下载地址和页签。邮件管理保持仅管理员可见，同时保留服务端校验。 |
| 账号 | 当前登录邮箱、退出登录 | 沿用退出确认、清除会话及隔离逻辑。 |

**操作留在发生的位置。** 搜索、筛选、分页、立即同步邮箱、手动补录、行内改状态、跨页勾选与“对比选中”仍在台账工作区。移动端用菜单按钮打开可关闭的侧栏；点选后收起，Esc 可关闭，焦点返回触发按钮。全宽只保留一个当前主内容区，表格可以在自己的容器内横滚。

**范围约束**：不新增 Agent 对话、聊天气泡、悬浮助手或空页面。不借侧栏改动重写鉴权、采集插件、邮件同步、提醒、台账状态机或统计口径。保留 `/?app=<id>`、`/?panel=reviews`、`settings`、`career&apps=…`、`mail-admin`、`plugin-connect`、`plugin-sites` 对应的原查询链接，以及 `/r/<token>` 提醒落地页。登录页和提醒落地页保持原流程。打开菜单、切换选中态、刷新页面都不能新增业务写入或重复触发模型请求。

## 二、单岗位匹配结果的阅读顺序

报告头部标明公司、岗位、使用的简历版本和分析时间。台账里的 **2–6 岗横向对比** 和 **未投递岗位推荐** 各自保留；单岗位报告有自己的正常入口和结果，不要求用户凑第二个岗位。

### 1. 核心匹配结论

并列展示**能力匹配度**和**投递优先级**，每项各有一句依据，下面给一句总体建议。前者回答“我能否做这份工作”，后者回答“按我已确认的偏好和当前条件，要不要优先投”。例如，技能与项目高度相关，但用户尚未确认能否在指定城市线下工作，可提示“专业能力匹配；先确认办公地点，再决定投递优先级”。能力材料不足不能直接写成能力不足；偏好材料不足可显示“优先级待确认”。产品评审前使用有证据的文字结论；数字示意仅可出现在标明示意的设计稿中，不自行确定公式、权重、分数区间或录用概率。

### 2. 硬性门槛检查

逐项展示 **岗位要求｜用户对应信息｜判断结果｜判断依据**。判断结果只用“满足／不满足／信息不足／需要用户确认”。工作许可、最低工作年限、指定城市线下办公等只有在 JD 明确要求时才算门槛。材料缺失用“信息不足”，资料冲突或需本人表态用“需要用户确认”。若确有硬门槛不满足，顶部明确指出哪一条影响投递，并抑制“适合投／优先投”等无条件建议；普通维度优势不能抵消。JD 未列明门槛时如实说明。

### 3. 六维匹配分析

每个维度独立成卡。每张卡均有 **维度名称、岗位要求、用户证据、匹配结论、匹配优势、能力缺口、证据来源、下一步建议**。卡片结论限定为“匹配／部分匹配／不匹配／无法判断”。桌面可以双列，窄屏单列。卡头先给判断，详情给短引文和解释，长证据可展开。

| 维度 | 判断问题与可用证据 |
|---|---|
| 硬性门槛 | 引用上一节检查项汇总，用同一份数据，确保汇总与明细一致。 |
| 技能工具 | 区分“提到 Tableau”和“用 Tableau 完成过项目”，对照 JD 要求的熟练程度。 |
| 经历项目 | 对照岗位职责与项目中的具体职责、承担范围、交付物。 |
| 行业业务 | 对照产品类型、客户场景和行业经历，说明哪些经验可以迁移。 |
| 偏好地点 | 对照已确认的城市、通勤、远程或线下偏好；“本人偏好”与“雇主强制要求”分别标注。 |
| 成果量化 | 引用指标、业务结果或可验证的交付物。原文没有数字时不得补造数字。 |

### 4. 优势与缺口总结

将有证据的技能、项目、行业经验、成果整理为优势；将确有差距的能力与“暂缺案例／资料不足”分开展示。每条都能回到对应维度、JD 原文和用户侧证据。对于“未发现案例”，显示所依据的岗位要求及查阅过的简历或画像版本，避免把未提及某项能力写成用户不会。

### 5. 下一步行动

| 动作 | 点击后必须发生的事 |
|---|---|
| 优化当前岗位简历 | 针对该岗位展示可编辑的修改建议，关联原简历段落和 JD 要求；由用户决定是否采纳，保留原文。 |
| 补充缺失技能或经历 | 带入具体缺口打开补充表单，进入下述确认流程。 |
| 生成面试问题 | 在当前报告内展示与岗位要求和缺口相关的问题，保留加载、失败、重试反馈。使用任务按钮，无需聊天入口。 |
| 查看岗位详情 | 打开被分析的那条台账记录，返回时仍可查看原报告。 |
| 重新运行匹配分析 | 用当前有效证据生成新报告，保留上次报告与两次分析的关联。 |

## 三、匹配结果纠错必须形成闭环

允许用户在具体判断旁点“补充或纠错”。例如原结论为“未发现 Tableau 的实际使用案例”，用户填写“我使用 Tableau 完成过一个商业分析 Dashboard”。先展示**原判断、用户补充、将写入的画像字段或证据、适用范围**，允许编辑或取消。仅在用户确认后保存为“用户确认补充”，保留关联岗位、维度、报告和时间。用户确认的是这段使用经历，不应据此推断熟练程度、量化收益或其他项目。

确认成功后提供“重新分析”。新报告可引用新增证据；旧报告仍能展示当时的结论、当时使用的依据以及后续补充。取消、失败、重复提交、换号期间返回的请求都不能产生错误写入。已有“修正简历文本”会重置当前画像，应保留其原有用途，另行处理逐条报告纠错。

## 四、实施边界与顺序

1. **做基线并迁移导航。** 阅读 `web/assets/js/app.js`、`views/ledger.js`、`views/settings.js`、`views/career.js` 和 `web/assets/app.css`（视图均位于 `web/assets/js/`）。列出旧入口到新入口的映射，用相同测试账号和数据保留桌面、移动端基线。复用原 action、路由和 `data-test`；避免重复挂载、轮询、插件连接提示或会话过期回调。先独立验收侧栏。
2. **给报告补齐数据，再做五段展示。** 复用 `server/src/modules/career-ai/` 的简历解析、模型调用、证据校验及账号隔离。现有 compare 接口明确要求 2–6 岗；为单岗位增加兼容的服务入口，保留旧接口契约。报告记录账号、岗位、简历版本、JD/画像证据快照或可重建版本、结构版本与原文引用。逐项核验引文；缺 JD、缺简历、模型失败或证据不符时，分别展示缺失、重试或无法判断。浏览器不持有模型密钥。
3. **接通纠错与下一步行动。** 增量扩展报告、用户确认的证据和分析历史。若复用 SQLite 的 `ai_reports`，处理现有 `kind` CHECK 约束与旧库迁移。验证历史 compare/recommend 报告仍可读取，新增证据参与账号数据删除。生成建议、预览补充、确认画像均不得修改投递状态、投递日期、邮件或提醒。旧模型结果没有六维字段时继续显示原报告，可由用户发起新分析。
4. **交付可验证的结果。** 按下面用例回归，提交改动摘要、入口映射、迁移说明、实际执行的命令和结果、桌面与移动端截图、失败项和复现条件。侧栏和报告各自可验收；产品待定的评分项在交付说明中单列。

## 五、回归测试与验收用例

使用隔离账号和数据库。先跑既有用例建立基线，改动后同条件复跑；新增测试覆盖旧套件尚未断言的行为。记录实际通过数和失败原因。

| 用例 | 操作与可核对的预期 |
|---|---|
| 导航与权限 | 普通账号、管理员分别登录，逐项进入侧栏。账号邮箱正确，管理员入口按权限出现，直接访问也受服务端保护；登录与提醒落地页正常；退出后下个账号看不到上个账号的徽标、勾选、报告或弹窗。 |
| 台账与待确认 | 搜索、筛选、分页、补录、改状态、归档、处理一条待确认。检查台账 ID、业务结果和统计口径；待确认徽标随处理变化。跨“投递明细／看过没投”选择两个岗位，进入原对比并保留两条 ID。 |
| 工具与旧链接 | 打开提醒设置及数据授权正确页签，验证插件下载、安装指引、连接与站点管理、邮件管理。旧深链、刷新、前进后退和提醒两步确认正常；导航一次只挂载一个视图，既有业务动作只发起一次。 |
| 新旧分析共存 | 上传 PDF/DOCX、粘贴文本、修正与重试仍可用。单岗可生成五段报告；原 2–6 岗对比、未投递推荐、旧报告、已有选岗深链仍可用。分析前后核对台账业务字段、历史与提醒均无意外变更。 |
| 硬门槛与双结论 | 构造“技能强但明确不满足强制条件”“仅缺许可信息”“偏好冲突需确认”“全部满足”四类样例。核对四种门槛状态及来源。阻断项不得被技能优势抵消；能力结论与投递优先级可不同，页面无未经批准的数字。 |
| 六维与证据 | 对同一份测试 JD/简历逐卡核对六维和八个字段。弱资料、矛盾资料、无 JD、失实引文都不得生成肯定判断；每条总结能定位到依据，资料不足和明确不符可以区分。 |
| 纠错全链路 | 用 Tableau 示例分别执行取消、确认、双击确认、保存失败再重试、重跑。取消不改画像，确认仅新增一次证据，刷新后可见；新报告引用补充，旧报告可读且保持原文；另一账号不能读写任一对象。 |
| 行动与异常 | 逐一点击五项行动，确认真实产物、正确岗位和返回位置。模拟模型不可用、请求超时和快速换页，保留已有数据，给出恢复入口，旧响应不覆盖新页面。 |
| 视觉与可访问性 | 至少检查 1440px、1024px、390px 三种宽度。长邮箱、长岗位名、大徽标、长引文、空态和错误态无裁切。仅用键盘可完成打开导航、选择页面、展开证据、取消纠错与关闭抽屉；选中、焦点和门槛状态均可辨认。 |

优先复用 `npm test`、`npm run test:web`、`npm run test:career-ai`、`npm run test:panel`、`npm run test:mail-admin` 及 `npm run test:e2e`。单岗证据、门槛优先和纠错持久化补进 `server/test/career-ai.test.js`；导航、五项行动和新旧报告回看补进相应浏览器用例。模型桩验证交互和数据契约，另用脱敏样本人工核对判断与原文是否相符。
